# Независимые вложения заявок, заказов и клиентов

## Цель

Дать пользователю возможность прикладывать произвольные файлы и ссылки к заявке, подтвержденному заказу и клиенту независимо от признака `isByContract`.

Ключевые пользовательские сценарии:

- приложить XLSX-смету, PDF, DOCX, CSV, TXT или изображение к заявке до ее подтверждения;
- хранить договор, счет, чек, акт и произвольные материалы в одном блоке заказа;
- хранить общие документы клиента отдельно от документов конкретного заказа;
- открыть, скачать или удалить документ в Web/PWA и Android;
- добавить файл в Android без сети и отправить его после восстановления подключения.

## Зафиксированные продуктовые решения

- Пользовательское название функции: `Файлы и документы`.
- Галочка `По договору` не управляет видимостью или сохранностью файлов.
- Вложения доступны для `draft`, `active`, `closed` и `canceled`; статус влияет только на бизнес-действия, но не на доступ к ранее сохраненным материалам.
- Тип нового произвольного файла по умолчанию — `other`, а не `contract`.
- В MVP используется существующий тарифный флаг `allowDocuments`.
- Каноническое поле обеих сущностей — `documents[]`.
- Legacy-поля мероприятия (`documentFiles`, `contractLinks`, `invoiceLinks`, `receiptLinks`, `actLinks`) сохраняются для обратного чтения и миграции, но новые клиенты не должны в них писать.
- Отдельная MongoDB-коллекция файлов на первом этапе не создается.
- Один загруженный файл принадлежит одной сущности. Выбор файла клиента из заказа и совместное использование одного файла несколькими сущностями остаются за рамками MVP.
- Клиентские файлы добавляются после первого сохранения клиента; временные каталоги для еще не созданного клиента не вводятся.
- Максимальный размер одного файла — 5 МБ, чтобы Web/PWA и Android имели одинаковое ограничение.

## Владение файловым сервисом

`cloud.escalion.ru` — проект владельца ArtistCRM. Его API, правила хранения и выдачи файлов можно расширять под требования CRM. При проектировании нельзя считать текущий контракт Escalion Cloud неизменяемым внешним ограничением.

Работы разделяются между двумя управляемыми частями системы:

- ArtistCRM отвечает за пользователя, тариф, tenant, принадлежность сущности, бизнес-метаданные документа, UI и offline-очередь;
- `cloud.escalion.ru` отвечает за прием байтов, физическое хранение, приватную выдачу, метаданные, checksum и удаление объекта.

Изменения `cloud.escalion.ru` должны быть развернуты первыми и оставаться обратно совместимыми с существующим upload API до завершения миграции ArtistCRM.

## Целевая модель данных

Общая структура элемента `documents[]`:

```js
{
  id: 'uuid-or-fileQueueId',
  type: 'contract', // contract | invoice | receipt | act | other
  customTypeName: '',
  title: 'Договор №12',
  url: '', // внешняя ссылка или legacy URL
  file: {
    name: 'dogovor-12.docx',
    storageKey: 'vedelo/...',
    url: '', // legacy URL, не обязателен для новых приватных файлов
    path: '', // legacy path
    size: 12345,
    contentType: 'application/vnd.openxmlformats-officedocument.wordprocessingml.document',
    checksum: 'sha256:...'
  },
  createdAt: '2026-09-14T00:00:00.000Z'
}
```

Правила:

- `url` верхнего уровня хранит пользовательскую внешнюю ссылку;
- новый загруженный файл идентифицируется через `file.storageKey`;
- `file.url` и `file.path` сохраняются для обратной совместимости;
- для Android `fileQueueId` используется как `document.id`, поэтому повтор запроса не создает дубль;
- дедупликация выполняется по `id`, затем по `storageKey`, `path` или URL;
- название документа не содержит секретов, токенов или локальных путей устройства.

## Контракт ArtistCRM ↔ cloud.escalion.ru

### Авторизация

- К приватному API обращается только сервер ArtistCRM.
- Существующий `x-api-password` можно сохранить в первой версии контракта, но он никогда не передается в браузер или Android-клиент.
- Желательное усиление: отдельный service credential для ArtistCRM и подпись запроса с timestamp для защиты от повторного воспроизведения.
- В логах обеих систем запрещено выводить секрет, содержимое файла и персональные данные из формы.

### POST `/api/private-files/upload`

Назначение: загрузить один приватный файл.

`multipart/form-data`:

```text
file          binary, обязательно
storageKey    сформированный сервером ArtistCRM ключ/префикс
uploadId      UUID/fileQueueId для идемпотентности
```

Vedelo формирует ключ только после проверки сущности:

```text
vedelo/{tenantId}/events/{eventId}/documents/{uploadId}
vedelo/{tenantId}/clients/{clientId}/documents/{uploadId}
```

Новые загрузки после ребрендинга используют корень `vedelo`. Уже сохраненные
ключи с корнем `artistcrm` остаются валидными для чтения и удаления без
физического переноса файлов.

Escalion Cloud дополнительно проверяет допустимый корень, длину сегментов и отсутствие `..`, обратных слэшей и управляющих символов.

Успешный ответ:

```json
{
  "success": true,
  "data": {
    "storageKey": "vedelo/...",
    "name": "brief.xlsx",
    "size": 24831,
    "contentType": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
    "checksum": "sha256:...",
    "createdAt": "2026-09-14T00:00:00.000Z"
  }
}
```

Повтор с тем же `uploadId` возвращает метаданные ранее загруженного объекта и не сохраняет второй файл.

### POST `/api/private-files/access-url`

Назначение: получить короткоживущую ссылку на просмотр или скачивание.

```json
{
  "storageKey": "vedelo/...",
  "downloadName": "brief.xlsx",
  "disposition": "attachment"
}
```

Ответ:

```json
{
  "success": true,
  "data": {
    "url": "https://cloud.escalion.ru/...signed...",
    "expiresAt": "2026-09-14T00:05:00.000Z"
  }
}
```

Рекомендуемый срок жизни ссылки — 5 минут. Для PDF и изображений ArtistCRM может запросить `inline`, для XLSX/DOCX — `attachment`.

### DELETE `/api/private-files`

Назначение: физически удалить файл.

```json
{
  "storageKey": "vedelo/...",
  "deleteId": "uuid"
}
```

Удаление идемпотентно: отсутствие объекта считается успешным результатом. ArtistCRM удаляет метаданные документа только после успешного ответа облака либо сохраняет задание на повторную очистку.

### Ошибки облачного API

Единый формат:

```json
{
  "success": false,
  "error": {
    "code": "FILE_TOO_LARGE",
    "message": "Файл не должен превышать 5 МБ"
  }
}
```

Минимальный набор кодов:

- `UNAUTHORIZED`;
- `FILE_REQUIRED`;
- `FILE_EMPTY`;
- `FILE_TOO_LARGE`;
- `FILE_TYPE_NOT_ALLOWED`;
- `STORAGE_KEY_INVALID`;
- `UPLOAD_ID_INVALID`;
- `FILE_NOT_FOUND`;
- `STORAGE_UNAVAILABLE`.

## Этап 1. Общая модель и нормализация

1. Создать переиспользуемое описание документа в `schemas/documentSchema.js`.
2. Подключить его к `schemas/eventsSchema.js` без изменения существующих данных.
3. Добавить `documents: []` в `schemas/clientsSchema.js`.
4. Вынести общую нормализацию в `helpers/entityDocuments.js`.
5. Оставить совместимые экспорты в `helpers/eventDocuments.js`.
6. Добавить `documents` в `DEFAULT_CLIENT` и мобильный тип `Client`.
7. Добавить `storageKey` и `checksum` как необязательные поля, чтобы legacy-документы оставались валидными.

Критерий завершения: старые мероприятия читаются без миграции, новый клиент сохраняется с пустым `documents[]`, unit-тесты нормализации проходят.

## Этап 2. Независимые вложения заявки/заказа в Web

1. Обобщить `EventDocumentsEditor` в `DocumentsEditor`, оставив совместимый wrapper на время перехода.
2. Изменить название действия на `Добавить файл или ссылку`.
3. Сделать `Файл` и тип `Другое` начальными значениями модалки.
4. Подставлять имя выбранного файла в название документа.
5. В `eventFunc.js` убрать зависимость блока от `isByContract` и `!isDraft`.
6. Разделить предупреждение: финансовые операции недоступны заявке, файлы доступны.
7. Не менять и не очищать документы при переключении `isByContract`.
8. Сохранять документ через канонический `documents[]`.

Критерий завершения: пользователь прикладывает XLSX к заявке без галочки `По договору`, файл остается после сохранения и перезагрузки.

## Этап 3. Документы клиента в Web

1. В `POST /api/clients` и `PUT /api/clients/[id]` явно нормализовать `documents[]`.
2. Перед принятием непустого `documents[]` проверять `allowDocuments`.
3. Не принимать из клиентского JSON готовый произвольный `storageKey` для еще не загруженного файла.
4. Добавить в `clientViewFunc.js` секцию `Файлы и документы` с количеством, последними тремя элементами и действиями `Добавить`, `Показать все`, `Открыть`, `Удалить`.
5. После изменения обновлять `useClientQuery`, список клиентов и временное Jotai-состояние без полной перезагрузки.
6. Для нового клиента показывать загрузку только после получения серверного `_id`.

Критерий завершения: документ клиента доступен в его карточке и не появляется автоматически во всех заказах этого клиента.

## Этап 4. Приватная загрузка и скачивание

### В cloud.escalion.ru

1. Добавить три приватных endpoint из контракта выше.
2. Реализовать идемпотентность `uploadId`.
3. Ограничить файл 5 МБ и разрешить PDF, DOC/DOCX, XLS/XLSX, CSV, TXT, JPEG, PNG и WebP.
4. Запретить исполняемые и web-исполняемые файлы, включая EXE, MSI, BAT, CMD, JS и HTML.
5. Считать SHA-256 и возвращать checksum.
6. Добавить короткоживущие signed URL и безопасный `Content-Disposition`.
7. Реализовать идемпотентное физическое удаление.
8. Сохранить старый upload endpoint до окончания перехода ArtistCRM.

### В ArtistCRM

1. Расширить `server/escalionCloud.js` методами upload, access URL и delete.
2. Создать общий серверный валидатор файлов и безопасный builder `storageKey`.
3. Добавить entity-aware upload endpoints для events и clients; browser не передает физический каталог.
4. Перед upload/download/delete проверять авторизацию, `tenantId`, тариф и принадлежность сущности.
5. Отдавать браузеру только временную ссылку, не service credential.
6. Сохранять неудачное облачное удаление в повторяемую очередь очистки либо возвращать пользователю понятную ошибку без потери метаданных.

Критерий завершения: tenant не может загрузить, получить ссылку или удалить файл другой организации; новый Mongo-документ хранит `storageKey`, а не обязательный публичный URL.

## Этап 5. Android и offline

1. Разрешить event-file endpoint для `draft`.
2. Перевести новые Android-загрузки события с `documentFiles[]` на `documents[]`.
3. Использовать `fileQueueId` как `document.id` и ключ идемпотентности облака.
4. Добавить `/api/mobile/v1/clients/[id]/files` и удаление клиентского документа.
5. Научить `encryptedFiles.ts` маршрутизировать `events` и `clients` в entity-aware endpoints.
6. Сохранить поддержку старого `attachmentKind: documentFile` для уже существующей очереди.
7. Добавить экран `/clients/[id]/documents` и ссылку из карточки клиента.
8. После upload обновлять зашифрованный cache сущности и показывать документ без перезапуска.
9. Сохранять текущую локальную AES-шифрацию, retry и восстановление после process death.

Критерий завершения: файл клиента или draft-заявки, выбранный без сети, переживает перезапуск, загружается один раз после восстановления сети и открывается через системный share sheet.

## Этап 6. Миграция и обратная совместимость

1. Создать идемпотентную миграцию `documentFiles[] -> documents[]` для файлов, добавленных мобильным приложением после прежней миграции документов.
2. Дедуплицировать по `mobileUploadId`, URL и имени/размеру как последнему fallback.
3. Не удалять legacy-поля в этом релизе.
4. Читать документы через `mergeLegacyEventDocuments` до отдельного подтвержденного этапа очистки.
5. Новые приватные файлы не преобразовывать в постоянные публичные URL.
6. Старые публичные URL продолжать открывать напрямую либо через совместимый proxy.

Порядок развертывания:

1. обратно совместимое обновление `cloud.escalion.ru`;
2. ArtistCRM с поддержкой `storageKey`, но со старым чтением URL;
3. включение новой загрузки Web/PWA;
4. обновление Android;
5. миграция legacy-записей;
6. наблюдение за ошибками upload/access/delete;
7. отдельное решение об удалении legacy-кода после стабилизации.

## Roadmap и версия

Работа учитывается пунктами DOC-T4–DOC-T7 в `docs/ROADMAP.md`. Пока создается только план, пункты остаются `[ ]`, версия не меняется.

Закрытие всего обратно совместимого функционального блока является minor-релизом. Если к моменту завершения текущей останется версия `1.19.0`, целевая версия — `1.20.0`. Версия повышается только одновременно с фактическим закрытием roadmap-пунктов.

## Не входит в MVP

- папки и произвольная иерархия документов;
- версии одного документа;
- совместное редактирование XLSX/DOCX;
- полнотекстовый поиск внутри файлов;
- автоматическое распознавание реквизитов;
- автоматическое копирование файлов клиента в заказ;
- один физический файл с несколькими владельцами;
- неограниченное хранение без tenant-квот.
