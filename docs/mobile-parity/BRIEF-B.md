# Задание B+C — удаление developer-функционала из Android-приложения

Репозиторий: `~/projects/ArtistCRM`, ветка `codex`. Прочитай `AGENTS.md`, затем `docs/MOBILE_PWA_PARITY.md` (особенно §6.2 этапы B и C, §6.3, §7, §8.2) — это источник правды по задаче.

## Цель захода

В Android-приложении (`mobile/`) должен остаться **только функционал конечного пользователя**.
Всё, что доступно роли `dev` (владелец/разработчик платформы), из исполняемого кода приложения выкорчёвывается:
удаляется ветка кода, её состояние, зависимости и HTTP-вызовы — **не** `isDeveloper=false`, не CSS-hide и не «убрать пункт меню».

Реализуй ровно этапы **B** и **C** из `docs/MOBILE_PWA_PARITY.md` §6.2, с деталями из §7.

## Что именно удалить

**B — developer-ИИ** (`src/features/integrations/AiUsagePanel.tsx`, `ManagedIntegrationsSection.tsx`, `AiUsagePanel.test.tsx`):

- admin-модели `AdminAiUsage`/`AiBillingSettings`, prop `isDeveloper`, `developerPromise`;
- запросы `/ai/settings` (GET/POST), `/ai/usage?scope=admin`, сохранение коэффициента наценки;
- поля себестоимости/списаний/маржи/platform breakdown/топ пользователей;
- выбор и сохранение провайдера DeepSeek (`provider=deepseek`, admin-подписи API-key/model, привязка `canUseDeepseek`);
- оставить: личный баланс/пороги/доступность/личную историю `/ai/usage`, провайдера «ИИ Ведело» и собственный ключ AITunnel, pause/disconnect, платёжную историю, refresh/error/loading.
- Неизвестный/legacy сохранённый провайдер разбирать как несовместимое состояние, **не** перезаписывать серверные настройки автоматически.

**C — operator-поддержка** (`app/support/index.tsx`, `app/support/[id].tsx`, `src/features/support/api.ts`, guard в `app/(tabs)/more.tsx`):

- режим «Обращения пользователей», developer-инбокс, панель автора/смены статуса, inversion «собственное = developer»;
- `updateSupportTicketStatus` и PATCH статуса;
- оставить: пользовательский список/создание/переписку/ответ/прочтение/вложения; входящие с `authorRole='developer'` — как сообщения собеседника.
- **Важно (§7, абзац «Ограничение поддержки»):** сервер считает роль `dev` оператором и убирает у него tenant из выборки. Поэтому для bearer с ролью `dev` Android **не должен** вызывать list/detail/create/reply/read/summary вообще (guard до сети, включая счётчик непрочитанных в меню и прямое открытие route) — показать понятное сообщение, что этот режим в пользовательском приложении недоступен. Это защита от глобальных запросов, а не сохранение operator-функции. Роль в payload/локальной сессии не понижать.

## Жёсткие границы

- Меняются только файлы внутри `mobile/`. Web-часть (`app/`, `server/`, `layouts/`, `helpers/`, `components/`, `models/`) не трогать.
- **Не редактировать** `mobile/src/shared/storage/**`, `mobile/src/shared/sync/**`, схему SQLCipher, outbox, ключи кэша, `operationId`, tombstones, файловые очереди.
- Не менять package ID, deep-link схемы, EAS-конфигурацию, `app.json`, `eas.json`.
- Не удалять по слову «dev»: `authorRole: 'developer'`, тариф с именем DEV, development EAS-профиль, dev-схемы deep link, `deviceName`, роль в auth-метаданных, личные рефералы, биллинг и выбор своего тарифа, `/sync` и личные интеграции.
- Не менять серверный код и мобильный API-контракт.
- Файл `mobile/src/shared/notifications/index.ts` (неотслеживаемый, чужая параллельная работа) **не трогать** — известная исходная ошибка typecheck не наша. Не «чинить» её.
- В рабочей копии есть чужие незакоммиченные изменения — не откатывать, не удалять, не коммитить.
