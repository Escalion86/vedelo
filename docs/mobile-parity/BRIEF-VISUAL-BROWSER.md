# Браузерная приёмка визуального паритета

Создай и исполни воспроизводимый браузерный тест `tests/components/mobileVisualParity.browser.test.cjs` (можно добавить файл fixture рядом) для настоящих Android-компонентов через React Native Web и настоящих стилей текущей PWA. Только тесты, фикстуры и отчёт `docs/mobile-parity/REPORT-VISUAL-BROWSER.md`, никаких изменений production исходников, git, конфигов и версий. Этапы 1 и 2 сейчас правят компоненты: во время твоей работы их состояние может обновляться, родитель повторит тест после завершения. Не жди их и не выдавай текущий прогон за окончательную приёмку.

- В тесте разрешай окружение ESBUILD_MODULE/RN_WEB_MODULE/PLAYWRIGHT_MODULE/QA_SCREENSHOT_DIR; без зависимостей явный skip, с DS_REQUIRE_BROWSER=1 отсутствие зависимости ошибка.
- Не устанавливай ничего в рабочий проект и не изменяй package*.json. Для временных файлов только `/home/aleksei/.hermes/cache/scratch`.

## Проверяемые поверхности

Настоящие `QuickContacts`, `MobileEventCard`, `MobileClientCard`, `AttentionScreen` и `TaskCard`, `ThemeProvider` forcedMode без storage. Не создавай вручную HTML-рисунки этих компонентов. В изолированном стенде разрешены явно названные тестовые фикстуры вместо query-cache/router/auth/storage/сетевых запросов — это проверка рендера/кликов, не БД или реального APK. Не вытягивай персональные данные и production API.

Expo-зависимости при необходимости заменяй только на уровне стенда (esbuild plugin). Для иконок сохраняй реальные glyphMap и настоящие шрифты из `mobile/node_modules/@expo/vector-icons`; недопустимо заменять все иконки текстом, пустыми svg или одинаковым символом и затем утверждать визуальный паритет. Если удастся напрямую загрузить Expo fonts — лучше. Стенд обязателен с реально загрузившимися шрифтами.

Для контактов дополнительно отрендери настоящий веб `ContactsIconsButtons` с `.contact-quick-button` и настоящим CSS (при помощи существующего Tailwind/compiler или с текущим готовым CSS). Веб-моки UI/query зависимостей допустимы; размеры/цвета и значки берутся из реального JSX и CSS. Если полный веб-компонент не получается, честно назови ограничение, но нативные компоненты всё равно проверь и сохрани измерения.

## Сценарии

1. 360/390/420 и обе темы: телефон+пробные каналы, все подтверждённые каналы, приоритет, MAX, источники Cigam, длинные названия/ФИО, допконтакты. Имеющиеся каналы доступны без выхода за карточку; отдельно наличие/положение раскрытия на узком экране. Рамка/фон/значки контактов и нейтральный бейдж снять через computed styles.
2. «Важное»: заполненные разделы с overdue/today/tomorrow, выполненной задачей doneAt, прошедшей заявкой, без шага, предстоящей работой и значимой датой. Реально измерить рамки/полосы/счётчики, отсутствие переполнения/перекрытия, клики меню/завершения/сводки по текущему представлению. Пустой обзор тоже проверить.
3. Контакты не должны запускать открытие карточки; выход из меню, disabled и соответствующая ссылка по mock роутеру/Linking. Никаких реальных мутаций.
4. Живое изменение размера окна, не только статичный экспорт. Сохранить screenshots PNG и HTML со всем `style.sheet.cssRules` для последующих гейтов.
5. Запустить vendored gates по правильным HTML: `verify_target_size`, `verify_responsive`, `verify_overflow`; только фактические результаты, ошибки не скрывать. Не исправлять production, найденные дефекты описать родителю.

## Отчёт

На русском: команды, фактический вывод, результаты/ограничения, абсолютные пути скриншотов/HTML/измерений. Источники тестовых данных явные. Визуальный браузерный стенд не заменяет нативный Android-рендер и приёмку на телефоне. Довести до реального запуска, не только написать тест.
