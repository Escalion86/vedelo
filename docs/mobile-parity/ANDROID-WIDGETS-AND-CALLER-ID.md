## Реализованный прототип и открытые проверки

- `mobile/modules/vedelo-device`: локальный Expo Kotlin-модуль, API 29+, без зависимости от GMS для определителя/контактов/города/виджета. `mobile/plugins/withVedeloDevice.js` сохраняет разрешение наложения после prebuild.
- `ProjectionStore`: AES-GCM, Android Keystore, AtomicFile в noBackupFilesDir; только имена/номера, открытые работы и следующие контакты. Токен поколения привязан к аккаунту; синхронный выход очищает файл и виджет. Зарезервированная ревизия публикации исключает перестановку запоздавших обновлений. В снимке нет bearer-токенов или ключа SQLCipher.
- `VedeloCallScreeningService`: немедленно разрешает входящий звонок до чтения диска, затем ищет локально. `CallerLookup` учитывает дополнительные контакты работы, текущий интервал и будущие даты, исключает closed/canceled. Неоднозначность, неизвестный номер, отсутствие и возраст копии отображаются отдельно. Имя из телефонной книги — дополнительный источник, сеть не используется.
- Карточку можно переместить, закрыть и открыть клиента/работу; при отсутствии наложения используется private-уведомление. По умолчанию при блокировке сведения скрываются. Реальное положение относительно кнопок звонилки, исходящие вызовы, запуск без интерфейса и отзыв разрешений **не проверены**.
- `WorkSummaryWidget`: RemoteViews, компактный/расширенный режим, WorkManager каждые 30 минут читает последнюю копию; изменения cache/sync обновляют её отдельно. По умолчанию виджет показывает обезличенную сводку даже на разблокированном экране: launcher может сохранить RemoteViews после остановки процесса. Детали включаются явной настройкой показа на блокировке.
- `/native/contacts`: чтение только по запросу и разрешению, выбор основного номера, предпросмотр выбранных контактов, поиск дублей по всем известным номерам; импорт только после подтверждения. Дополнительные номера сохраняются в комментарий только по отдельному выбору. Обратное сохранение клиента открывает системную форму.
- `DetectTownButton`: coarse location, LocationManagerCompat и Geocoder, ограниченное ожидание, в JS возвращается город/регион без координат. Поздний результат не заменяет ручной ввод; применение подсказки отдельной кнопкой. Кнопка есть в первом запуске и настройке города.
- Ярлыки заявки/клиента/голосового ввода; необязательная биометрия с системным PIN, холодный запуск и 60 секунд в фоне или с выключенным экраном. PrivacyReceiver и lifecycle отмечают неактивность нативно; AppLockClock использует SystemClock.elapsedRealtime (включает сон), не сбрасывает начало на повторном pause и снимает требование только после успешного подтверждения для текущего поколения сессии. JS слушает change/blur/focus и перечитывает нативное состояние. Повторный resume не раскрывает проекцию. Есть тесты отмены, cold start, минуты без AppState background, повторных событий и смены аккаунта во время подтверждения; проверка кнопки питания на телефоне открыта.
- Ручной итог: `/native/call-result`, SQLCipher `__android_call_result`, общий cookie/bearer API `/api/calls/android`, отдельный источник Calls.provider=android. RequestId/fingerprint и детерминированный ID задачи обеспечивают повтор; неизвестная длительность — null. Список доступен Android и PWA без тарифа IP-телефонии. На временной MongoDB прошли 4 проверки, component/store — 3; испытания с реальными звонками ещё нужны. Дата сохранения явно отделена от неизвестного времени начала разговора.
- Единая очередь переходов (`+native-intent`, `native/intents`, `/native/open`) добавлена после сборки прототипа: whitelist пользовательских адресов, сохранение до входа, ожидание разблокировки, проверка доступа к записи, очистка при смене аккаунта. 18 unit/component проверок прошли; на устройстве ещё не проверена.
- Share Target: `ShareReceiverActivity` принимает SEND/SEND_MULTIPLE и ClipData; `/native/share` показывает текст, список файлов и миниатюры изображений. Текст передаётся в обычную заявку/клиента или редактор ИИ без сохранения/анализа. Файлы выбираются отдельно, затем по явному нажатию попадают в зашифрованную очередь документов конкретной записи. Стабильный ID вложения исключает повтор очереди при потере ответа; сервер повторно проверяет доступ при отправке.
- **Открыты:** приёмка Share Target, privacy всех push, RuStore Push, обновление поверх production APK, device QA. Эти возможности не считать завершёнными по наличию Kotlin-модуля.

## Push без Google: текущая реализация и настройка

`MobilePushSubscriptions` и `/api/mobile/v1/push/subscription` заменяют регистрацию
новых APK: tenant/user/session/installation, один provider, revision и deliveryId.
Отозванные/истёкшие сессии не участвуют в доставке; старые Expo-подписки устройств,
перешедших на реестр, исключаются из legacy-отправки. Отключение относится к текущей
сессии; запоздалый ответ не активирует native push после выхода/отключения.

RuStore SDK 7.5.0 проверяет доступность дистрибьютора; при доступных Google services
выбирается Expo/FCM. Config plugin добавляет репозиторий, init в Application и FCM
receiver. Оба новых транспорта передают data-only: Kotlin проверяет поколение,
провайдер и messageId до показа, не запуская JS. По умолчанию текст обезличен;
подробности включаются существующей явной настройкой. Выход отменяет уведомления.
Быстрые кнопки выполнения/переноса задач открывают предпросмотр `/native/task-action`;
сохранение выполняется явным подтверждением после входа/разблокировки/проверки заказа.
Обычный переход идёт через ту же очередь. На телефоне эти переходы ещё не проверены.

Проект RuStore у владельца **ещё не создан**. Настройка после проверки подписи:

1. В RuStore Console создать Push-проект для `ru.escalion.vedelo` с отпечатком
   production-сертификата. Для Dev — отдельный проект `ru.escalion.vedelo.dev` и его
   debug-сертификат из описания артефакта выше. Эти проекты не взаимозаменяемы.
2. Public `RUSTORE_PUSH_PROJECT_ID` передать в окружение prebuild и сервера;
   `RUSTORE_PUSH_SERVICE_TOKEN` хранить **только на сервере**. Для Dev — суффикс `_DEV`.
   Значения не отправлять в чат и не коммитить. Примеры переменных добавлены в `.env.example`.
3. Выпустить новую APK-сборку и проверить доставку/переходы/отзыв разрешений,
   блокировку/смену аккаунта/выход и отсутствие дублей на GMS и non-GMS устройствах.
   Ротация RuStore token при остановленном JS сейчас регистрируется при следующем
   открытии приложения; это остаётся ограничением до отдельного фонового механизма.

[типы Expo push](https://docs.expo.dev/push-notifications/what-you-need-to-know/).
Реальная доставка пока не проверена; компиляция не заменяет приёмку на телефоне.

## 1. Виджет рабочего стола (M1-T9)

- Ближайшее мероприятие/заказ и следующий контакт, просроченные задачи; переход в соответствующие карточки и действие создания заявки.
- Данные из последней локальной копии текущего аккаунта; подпись времени обновления и состояния отсутствующих/непрочитанных данных. Фоновые обновления ограничены Android, постоянную свежесть не обещать.
- При выходе, смене аккаунта и отзыве доступа очищать проекцию и активные виджеты; не переносить данные между tenant. На заблокированном устройстве учитывать выбранную политику приватности.
- Нативный Android-модуль и воспроизводимый Expo config plugin; новая development/preview-сборка. Expo Go для проверки недостаточен. Package ID и схемы переходов сохраняются.

## 2. Определитель входящих и исходящих звонков (M1-T8)

Первый кандидат — `CallScreeningService` и системная роль `ROLE_CALL_SCREENING` на Android 10+. Получение роли добровольное; объяснять замену другого определителя. Обычную звонилку не заменять, вызовы не блокировать.

- Получать номер и направление обычного телефонного вызова, включая запуск при закрытом интерфейсе. Работа после принудительной остановки приложения не гарантируется.
- Номера из телефонной книги и требование `READ_CONTACTS` проверить отдельно. Скрытые/недоступные номера не восстанавливать и не угадывать.
- Звонки мессенджеров, запись звука, длительность/факт ответа и чтение общей истории не входят в первый объём: получение номера не даёт этих возможностей.
- Не добавлять `READ_CALL_LOG`/SMS-разрешения. Выпуск — APK/RuStore; Google Play исключён из текущей задачи.
- После разговора предложить результат/заметку и следующий контакт. Не создавать серверную запись автоматически без согласованного контракта и защиты повторов.

## 3. Всплывающая карточка входящего звонка

Основное требование владельца: во время входящего звонка показать, найден ли клиент, его ФИО/данные и ближайшее связанное мероприятие с кратким описанием.

- Компактное окно поверх экрана вызова, не перекрывающее ответ/отбой; закрытие и перемещение. Переходы «Открыть клиента» и «Открыть мероприятие/заказ» через существующие маршруты, с проверкой авторизации.
- Нормализованный номер сопоставлять с локальными контактами текущего tenant, включая допустимые дополнительные номера. Несколько совпадений обозначать явно, без молчаливого выбора.
- Ближайшая предстоящая связанная работа: дата/время, заголовок/тип и короткое описание; canceled/closed исключить, draft явно обозначить. Неизвестную дату не выдавать за ближайшую; правила текущего/уже начавшегося мероприятия уточнить по коду при брифе.
- Различать «Клиент не найден в последней копии», «Данные пока недоступны», «Номер скрыт», «Несколько клиентов», «Нет предстоящих мероприятий». Ошибка базы или отсутствие синхронизации не доказывают отсутствие клиента.
- Сначала своевременно разрешать входящий вызов штатным ответом Android, затем искать/показывать контекст; не ждать сети внутри системного срока ответа.
- Для наложения проверить необходимость специального разрешения `SYSTEM_ALERT_WINDOW` и ограничения целевой версии Android/прошивки. При отказе — обычное уведомление, если оно разрешено; отсутствие обоих разрешений объяснять в приложении. Не использовать AccessibilityService как обход ограничений.
- По умолчанию ФИО и описание не раскрывать на заблокированном экране. Отдельное явное согласие на показ персональных данных; проверить отсутствие утечки через уведомления, экран недавних приложений и журнал.
- Не сохранять открытый текст телефонов/ФИО в общих настройках. Использовать минимальную зашифрованную проекцию без зависимости от запущенного JS; SQLCipher и очередь синхронизации остаются основным хранилищем приложения.

## 4. Порядок работ и приёмка

1. Завершить T (AJ) и существующую приёмку U (AK) либо честно зафиксировать её внешние блокеры.
2. Отдельный бриф нативного прототипа: разрешения/роль, получение входящего и исходящего номера, карточка при закрытом интерфейсе, отказ роли и разрешений. До теста на реальном телефоне не объявлять техническую приёмку завершённой.
3. Отдельный заход интеграции с зашифрованной локальной базой и безопасностью tenant/выхода; тесты нормализации, неоднозначности и выбора работы.
4. Отдельный заход виджета рабочего стола и его обновления/очистки.
5. Одна согласованная Android-сборка и телефон: известный/неизвестный/скрытый номер, контакт телефонной книги, несколько совпадений, offline, закрытое приложение, блокировка экрана, отказ уведомлений/наложения, выход/смена аккаунта, отменённая/закрытая/черновая работа. Дополнительные прошивки — отдельная приёмка.
