## Правила, которые нельзя нарушать

1. **Перед началом:** `git fetch origin codex` и `git rev-list --left-right --count origin/codex...HEAD`.
2. Меняй только файлы внутри `mobile/` и `docs/`. Web-код (`app/`, `server/`, `layouts/`, `helpers/`,
   `components/`, `models/`, `schemas/`, `state/`) не трогай.
3. **Не редактируй** `mobile/src/shared/storage/**` и `mobile/src/shared/sync/**` (схема SQLCipher, outbox,
   ключи кэша, `operationId`, tombstones, файловые очереди) — только используй существующие экспорты.
4. Не меняй package ID, deep-link схемы, `app.json`, `eas.json`, push-настройки, серверный код и мобильный
   API-контракт.
5. В рабочей копии есть **чужие незакоммиченные файлы** — не трогай, не коммить, не откатывай:
   `mobile/package-lock.json`, `mobile/assets/notification-icon.png`, `mobile/src/shared/config/deepLink.js`,
   `mobile/src/shared/notifications/index.ts`, `app/v1/`, `app/api/events/[id]/quick-actions/`,
   `app/api/events/voice-transcribe/`, `app/api/push/expo/test/`, `helpers/deepLink.js`,
   `helpers/use{Services,SiteSettings,Tariffs,Users}Query.js`.
6. Коммиты адресные: `git add <конкретные файлы>`, **никогда** `git add -A`. Один заход = один коммит
   `feat(mobile): <этапы> — <суть>`. Не пушить, не открывать PR, не применять `reset --hard`/`checkout --`.
7. Сохранение сущностей — существующими мутациями/outbox, не прямым POST; offline-поведение не ломать.
8. Внутренние идентификаторы `events`/`eventId` и legacy-совместимость не переименовывать; склонения брать
   из `helpers/workItemTerminology.mjs` и мобильного resolver.
9. Developer-функционал не возвращать ни в каком виде (включая сетевые вызовы).

## Как работать

1. Возьми очередной заход из `docs/mobile-parity/PLAN-CONTINUE.md` (порядок: H → I → J → K → L → M → N →
   O → P → Q → R → S → T → U). Первый — **H: этапы P + Q**, вкладки редактора «Клиент и контакты» и
   «Финансы и Документы».
2. Составь бриф `docs/mobile-parity/BRIEF-<буква>.md` по образцу `BRIEF-G.md`: цель, файлы, критерии
   приёмки, что нельзя трогать, проверки, путь отчёта.
3. Выполни этапы захода целиком. Каркас трёх вкладок и `EventGeneralSection` уже существуют — новые секции
   наследуют общий draft, переключение вкладок и ошибка сохранения не теряют введённое.
4. Прогони проверки и **приведи вывод**:

```bash
cd mobile && npm run typecheck   # допустима ровно одна исходная ошибка: src/shared/notifications/index.ts:8
cd mobile && npm test            # baseline: 56 наборов / 343 теста — не меньше
cd .. && git diff --check
```

5. Отчёт `docs/mobile-parity/REPORT-<буква>.md`: что реализовано, какие правила закреплены тестами, что
   осталось, вывод проверок, риски, что не проверено на устройстве. Обнови `docs/mobile-parity/STATUS.md`.
6. Коммит **не делай** — коммитит владелец после проверки.

## Ограничения среды

- Визуальная приёмка на устройстве недоступна: `adb`/Java нет, нужна EAS preview-сборка и телефон.
  Отмечай такое как непроверенное, не выдавай за проверенное.
- `mobile/node_modules` уже установлены. Корневые `node_modules` для web-ESLint на этой машине нестабильны —
  в этом треке проверки = `typecheck` + `jest` внутри `mobile/`.
- Если этап упирается в отсутствующий серверный контракт (часовой пояс/длительность/передача в W,
  Telegram Business в Z, import-auth в Q, user-scoped переписки в K) — не имитируй функцию на клиенте,
  а зафиксируй пробел в отчёте.

Начни с чтения `AGENTS.md`, `docs/MOBILE_PWA_PARITY.md` (§4–§6) и `docs/mobile-parity/PLAN-CONTINUE.md`,
затем составь `BRIEF-H.md` и выполни заход H. Отвечай на русском языке.
