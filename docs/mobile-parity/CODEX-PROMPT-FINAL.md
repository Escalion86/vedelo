# Итоговый промпт для Codex: довести Android-приложение до паритета с мобильной PWA «Ведело»

Готов к вставке первым сообщением в новый чат. Копировать целиком (текст ниже разделителя).

---

Ты работаешь в репозитории **«Ведело»** — это Next.js CRM (`app/`, `server/`, `layouts/`, `components/`,
`helpers/`) плюс Android-клиент на Expo/React Native в каталоге `mobile/`. Мобильная PWA — это тот же
Next.js-проект, то есть **эталон поведения и вида — веб-код в этом же репозитории** (мобильные экраны,
mobile-first разметка, `components/MobileBottomNav.js`, `layouts/content/*`, `layouts/cards/*`).

Задача: **довести Android-приложение до близкого к мобильной PWA паритета — только пользовательские
функции.** Меню и функции разработчика/админа (админ-ИИ, operator-поддержка, админские разделы) уже
вырезаны из клиента в этапах B–C и возвращать их нельзя: для разработчика планируется отдельное приложение.

## 1. Первым делом — git (здесь уже была ошибка, не повторяй)

1. Рабочий репозиторий — **`git@github.com:Escalion86/vedelo.git`**. У проекта исторически есть **второй,
   устаревший** репозиторий `Escalion86/ArtistCRM.git` — работать в нём нельзя.
2. Выполни `git remote -v`. Если `origin` указывает на `ArtistCRM.git` — **остановись и скажи об этом**:
   это клон, отставший на 23+ коммита (версия 1.20.x против 1.32.x), любая работа в нём уйдёт в сторону.
   Нужен клон `vedelo`. На Orange Pi он уже есть: `~/projects/vedelo` (там же установлены зависимости).
3. Дальше: `git fetch origin`, `git status --short`, `git log --oneline -20`, `git branch -a`.
4. **Рабочая ветка.** Коммиты паритета лежат в ветке **`mobile-parity`** (на момент передачи — 14 коммитов
   поверх `origin/codex`: этапы A–O и выравнивание ALIGN). Если она уже влита в `codex` — работай в `codex`.
   Правило простое: `git log --oneline -20` должен показывать коммиты вида `feat(mobile): …` и
   `docs(mobile): …`; если их нет — ты не в той ветке, разберись до начала работы.
5. Никогда не используй `git add -A`, `git reset --hard`, `git checkout --` и не переписывай историю.
   Коммиты адресные, только по файлам своего захода. **Не пушь** — публикует владелец.

## 2. Что уже сделано (не переделывать)

Этапы **A–O** плана и выравнивание **ALIGN**: удалён developer-функционал, введены токены светлой/тёмной
темы и базовые UI-примитивы, переделана нижняя оболочка (`Важное / работы / [+] / Клиенты / Меню`),
сделан экран «Важное» с offline-действиями задач, список и карточка работ с фильтрами-оверлеем, просмотр
работы и каркас трёхсекционного редактора (готова вкладка «Общие»), плюс исправлены два дефекта веб-PWA
(Telegram по телефону на карточке пользователя, VK-аватар в просмотре пользователя).

## 3. Документы (прочитать перед работой)

- `docs/UI_CONVENTIONS.md` — правила UI/темы.
- `docs/MOBILE_PWA_PARITY.md` — разбор отличий Android ↔ PWA, дизайн-контракт (§4), анатомия экранов и
  компонентов (§5), этапы (§6.2), контрактные пробелы (§6.3), список удалённого developer-функционала (§7).
- `docs/mobile-parity/PLAN-CONTINUE.md` — **остаток работ по заходам** (что делать дальше и в каком порядке).
- `docs/mobile-parity/STATUS.md` — состояние работ; обновлять после каждого захода.
- `docs/mobile-parity/BRIEF-*.md` и `REPORT-*.md` — образцы брифов и отчётов, `REPORT-ALIGN.md` — что
  выровнено с текущей версией PWA.

## 4. Что делать

Идти по заходам из `PLAN-CONTINUE.md` в порядке: **H (P+Q) → I (R+S) → J (T+U) → K (V+W) → L (X) → M (Y) →
N (Z) → O (AA+AB) → P (AC+AD) → Q (AE+AF) → R (AG+AH) → S (AI) → T (AJ) → U (AK)**.

Каждый заход:

1. Составь бриф `docs/mobile-parity/BRIEF-<буква>.md` по образцу `BRIEF-G.md`: цель, конкретные файлы,
   критерии приёмки, что нельзя трогать, проверки, путь отчёта.
2. Реализуй заход целиком — сверяясь с **текущим веб-кодом** (не по памяти и не по старым отчётам).
3. Прогони проверки, приведи вывод (см. §6).
4. Отчёт `docs/mobile-parity/REPORT-<буква>.md`: что сделано, какие правила закреплены тестами, что
   осталось, что не проверено на устройстве, найденные пробелы API.
5. Обнови `docs/mobile-parity/STATUS.md`. Коммит **не делай** — коммитит владелец после проверки.

Порядок обязателен там, где есть зависимости (P → Q используют общий каркас редактора; AC/AD — перед AE/AF;
AJ — только после перевода всех пользовательских экранов).

## 5. Жёсткие границы

1. Меняются только `mobile/**` и `docs/**`. Веб-код (`app/`, `server/`, `layouts/`, `helpers/`,
   `components/`, `models/`, `schemas/`, `state/`) — только **читается** как эталон, не правится.
2. **Не редактировать** `mobile/src/shared/storage/**` и `mobile/src/shared/sync/**`: схема SQLCipher,
   outbox, ключи кэша, `operationId`, tombstones, файловые очереди. Только использовать существующие экспорты;
   сохранение сущностей — существующими мутациями/outbox, никогда прямым POST вместо очереди.
3. Не менять package ID, deep-link схемы (`vedelo://`, legacy `artistcrm://`), `app.json`, `eas.json`,
   push-настройки, серверный код и мобильный API-контракт.
4. Developer-функционал не возвращать ни в каком виде, включая сетевые вызовы.
5. Внутренние идентификаторы `events`/`eventId` и legacy-совместимость не переименовывать; склонения брать
   из `helpers/workItemTerminology.mjs` и мобильного resolver, не собирать вручную.
6. Чужие незакоммиченные файлы не трогать, не коммитить, не откатывать.

## 6. Проверки (выполнять обязательно, вывод приводить в отчёте)

```bash
cd mobile && npm run typecheck     # ожидается чисто, без ошибок
cd mobile && npx jest --runInBand  # baseline: 58 наборов / 349 тестов, полный прогон ~4-5 минут
git diff --check
```

Ухудшение этих чисел = регрессия. На слабой машине полный `jest` идёт несколько минут — это нормально.
Известная особенность (уже исправлена в ALIGN, следи, чтобы не вернулась): тест «overlay отдельно от
списка…» в `mobile/src/shared/ui/primitives.test.tsx` требовал таймаута больше 5 с при холодном полном
прогоне. Ослаблять сами проверки нельзя — можно только точечно поднимать таймаут.

## 7. Ограничения среды и контрактные пробелы

- **Визуальная приёмка на устройстве недоступна:** на Orange Pi нет `adb` и Java. Проверка вида и жестов —
  только EAS preview-сборка и телефон владельца (заход U). Не выдавай непроверенное на устройстве за проверенное.
- **Не имитируй отсутствующие серверные возможности.** Если функция упирается в контракт, которого нет в
  мобильном API (часовой пояс/длительность/передача в W, Telegram Business в Z, import-auth в Q, user-scoped
  переписки для блока сообщений в K, коммерческие предложения и адресные подсказки) — зафиксируй пробел в
  отчёте, не рисуй заглушку, выдаваемую за рабочий экран.
- Если веб-PWA за время работы успела измениться, **сверяйся с текущим кодом**, а не со старыми отчётами:
  за две недели в проект пришло больше 20 коммитов (MAX-мессенджер в контактах, «Отзывы клиентов», «Личный
  профиль», «Баланс и платежи», подпись «Создать <термин>» в нижней панели и другое) — уже сделанные экраны
  Android должны соответствовать текущей версии, а не вчерашней.
