# Персональный доступ и переход на скрытый тариф

Версия 1.37.0, 17 октября 2026 года. Изменения исходников; production и APK
не обновлялись. BRO — пример названия, код не привязан к нему.

## Для администратора

1. Создайте тариф в настройках тарифов: название, стоимость за месяц,
   возможности, отметка «Скрытый». Существующий скрытый тариф можно использовать
   без пересоздания.
2. Откройте пользователя → «Баланс и платежи» → «Сменить тариф».
3. В разделе «Доступ к скрытым тарифам» отметьте только нужные тарифы.
   Каждая галочка сохраняется сразу. Разрешение BRO не открывает другие
   скрытые тарифы и не меняет подписку/баланс.
4. Можно предоставить клиенту самостоятельный выбор либо выбрать тариф в поле
   «Тариф после окончания текущего периода» и нажать «Назначить после окончания
   текущего тарифа». Назначение скрытого тарифа одновременно разрешает только
   этот конкретный тариф.

Обычная кнопка «Сохранить» в верхней части прежней формы по-прежнему меняет
тариф немедленно, с оплатой нового месяца и выбранным режимом компенсации.
Не используйте её для отложенного перехода.

Пример: БИЗНЕС до 20 октября → назначить BRO после периода. БИЗНЕС сохраняется
до точного времени окончания; при следующем запуске продления после этого
времени списывается BRO. БИЗНЕС повторно не оплачивается.

## Для пользователя

В выборе тарифов появляются разрешённые скрытые тарифы с подписью
«Персональное предложение». Доступны обычное подключение сейчас и переход
после окончания текущего периода. Запланированный переход можно отменить
или заменить другим. Web/PWA и исходники Android поддерживают этот сценарий.
Для новых кнопок Android нужен выпуск обновлённого приложения; существующий
мобильный API остаётся совместимым.

Если оплаченный/пробный период уже закончился, следует выбрать подключение
сейчас. Само разрешение скрытого тарифа не отменяет автопродление текущего:
для этого нужен явный выбор перехода.

## Правила расчётов

- Выдача доступа и планирование не списывают деньги и не компенсируют текущий
  период. Дата перехода берётся сервером из срока текущей подписки.
- При переходе используется действующая на этот момент стоимость тарифа.
  Новый месяц начинается с фактического подключения, а не задним числом.
- При недостатке средств прежний платный тариф не продлевается. Пользователь
  переводится на публичный бесплатный тариф; если такого нет — тариф снимается.
  Переход и индивидуальный доступ сохраняются. После пополнения переход
  выполняется при следующем запуске существующего `/api/billing/renew`.
- Отмена ожидания после перехода на бесплатный тариф не восстанавливает старый
  оплаченный период. Для платного тарифа нужна обычная покупка.
- Отзыв конкретного разрешения отменяет запланированный переход на этот тариф.
  Уже подключённый скрытый тариф продолжает работать и продлеваться: это
  сохраняет совместимость с ранее назначенными скрытыми тарифами.
- Если тариф удалён, запланированный переход снимается при проверке продления;
  далее применяются обычные условия текущего тарифа.

## Контракт и защита

`GET/POST /api/billing/preferences` поддерживает web-сессию и mobile Bearer
через getRequestContext. По умолчанию используется текущий пользователь;
`?userId=…` другого пользователя допустим только для admin/dev.

POST принимает одну команду:

```json
{ "action": "grant", "tariffId": "ObjectId", "enabled": true }
{ "action": "schedule", "tariffId": "ObjectId" }
{ "action": "cancel" }
```

Grant разрешён только admin/dev и действует на один скрытый тариф. Смена
владельца/tenant, даты, цены или массива разрешений из payload не выполняется.
Конфликт сохранения возвращает 409; подмена пользователя — 403.

Список разрешений хранится в `Users.allowedTariffIds`. План —
`pendingTariffChange {tariffId, startsAt}`. Общая политика canSelectTariff
применяется в SSR, mobile, user PUT, создании платежей и применении оплаты.
Платёж, который пришёл после отзыва доступа, пополнит баланс, но не подключит
недоступный тариф; существующий обработчик сохраняет пояснение платежа.

Изменение подписки сравнивает снимок баланса, тарифа, дат, плана и
`billingRevision`. Списание и скрытая запись `pendingBillingReceipt` сохраняются
атомарно в Users. Payments дописываются по уникальному ключу tenant/user/операции.
При сбое дописывание повторяет cron, без повторного списания. Это восстановимая
операция для standalone MongoDB, не транзакция между коллекциями.

Миграция существующих пользователей не требуется; отсутствующая revision
считается начальной. Не удалять незавершённый pendingBillingReceipt вручную.
Отложенные переходы зависят от уже настроенного cron продления: новый внешний
планировщик не создавался.

## Проверка

- `node --test server/personalTariffs.mongo.test.cjs`: отдельный временный
  mongod, настоящие схемы и запросы; права, точечные разрешения, обход через
  user PUT, проверки обоих платежных провайдеров, гонки, компенсация,
  недостаток средств, отмена/отзыв, восстановление платежей и маршрут cron.
  Путь к mongod можно задать через `TARIFF_TEST_MONGOD`, иначе нужен mongod в PATH.
  Auth и внешние платёжные провайдеры в тесте заменены локальными адаптерами.
- `node --test server/mobile/billing.test.js server/billingRenewalState.test.js server/billingCalculations.test.js`.
- Android: `npm test -- --runInBand src/features/billing/BillingScreen.test.tsx src/features/billing/format.test.ts` из mobile.
- Точечный ESLint изменённых файлов и полная Webpack-сборка с
  `NODE_OPTIONS=--max-old-space-size=6144`.
- Браузерный стенд `scripts/personalTariffsQa.cjs`: реальные React-компоненты
  и CSS, фиктивные тарифы/HTTP-данные в памяти. Требует esbuild; путь к модулю
  задаётся `ESBUILD_MODULE`. Только localhost:4317. Проверены 390/1365 px,
  светлая/тёмная тема, отдельная галочка BRO при выключенном SECRET,
  назначение, самостоятельный выбор и отмена, консоль без ошибок.

Общий Android typecheck не проходит из-за ранее существующих конфликтов
CompactEventForm/compactEventForm и отсутствующих expo-image-picker/react-native-webview;
ошибок в изменённых billing-файлах нет. Проверки на физическом телефоне,
реальные платежи и production cron в этой задаче не выполнялись.
