## 1. Краткое резюме

1. **Разная основная навигация.** Android: «Главная / Мероприятия / Клиенты / Финансы / Ещё»; PWA: «Важное / Мероприятия / + / Клиенты / Меню». В Android нет центрального меню создания и нижнего подменю работ ([Android:31](../mobile/app/(tabs)/_layout.tsx#L31), [PWA:139](../components/MobileBottomNav.js#L139)).
2. **«Главная» не заменяет «Важное».** Есть три метрики, ближайшие четыре работы, финансы месяца и sync; задачи открываются отдельно. PWA объединяет задачи, задатки, закрытие прошедших, сообщения, даты клиентов и sync ([index.tsx:39](../mobile/app/(tabs)/index.tsx#L39), [tasks.tsx:17](../mobile/app/(tabs)/tasks.tsx#L17), [AttentionContent.js:16](../layouts/content/AttentionContent.js#L16)).
3. **Разные меню и полнота разделов.** Android группирует инструменты в «Работа / Организация», PWA использует `pagesGroups`; Android-экрана импорта/экспорта нет, настройки ограничены терминологией ([more.tsx:14](../mobile/app/(tabs)/more.tsx#L14), [section:33](../mobile/app/more/[section].tsx#L33), [pages:561](../helpers/constants.js#L561)).
4. **Палитра Android самостоятельная и только светлая.** `primary=#725B2F`, фон `#F6F4EF`, радиус Surface 18; PWA задаёт пары светлых/тёмных токенов, поверхности и состояния. В native root фиксирован `StatusBar style="dark"` ([theme.ts:1](../mobile/src/shared/ui/theme.ts#L1), [components.tsx:215](../mobile/src/shared/ui/components.tsx#L215), [globals.css:32](../app/globals.css#L32), [root:84](../mobile/app/_layout.tsx#L84)).
5. **Карточки устроены по-разному.** Android складывает информацию о работе вертикально, клиент — строка с аватаром, транзакция — строка с круглой иконкой. PWA использует разделители и колонки даты/содержимого/суммы, быстрые контакты и меню действий ([MobileEventCard:97](../mobile/src/features/events/MobileEventCard.tsx#L97), [clients:34](../mobile/app/(tabs)/clients.tsx#L34), [finance:100](../mobile/app/(tabs)/finance.tsx#L100), [design-qa:42](../design-qa.md#L42)).
6. **Фильтры расходятся по поведению.** Android: четыре scope-чипа работ, только поиск клиентов, четыре типа финансов. PWA: фильтры города/статуса/проверки/передачи, клиентские группы, период и связи транзакций, overlay без сдвига списка ([events:14](../mobile/app/(tabs)/events.tsx#L14), [EventsContent:1252](../layouts/content/EventsContent.js#L1252), [ClientsContent:185](../layouts/content/ClientsContent.js#L185), [TransactionsContent:303](../layouts/content/TransactionsContent.js#L303)).
7. **Редактор и просмотр работы функционально близки, но не равны.** В PWA три основные вкладки формы и отдельные финансовые KPI просмотра; Android — длинная форма с текстовыми датами и отдельный экран документов ([eventFunc:1654](../layouts/modals/modalsFunc/eventFunc.js#L1654), [eventViewFunc:601](../layouts/modals/modalsFunc/eventViewFunc.js#L601), [native edit:256](../mobile/app/events/edit/[id].tsx#L256)).
8. **Developer-функции действительно есть внутри пользовательских экранов.** Управление поддержкой, DeepSeek, наценка и платформенная статистика ИИ должны быть удалены из Android-кода, включая запросы ([support:16](../mobile/app/support/index.tsx#L16), [AiUsagePanel:133](../mobile/src/features/integrations/AiUsagePanel.tsx#L133), [ManagedIntegrations:421](../mobile/src/features/integrations/ManagedIntegrationsSection.tsx#L421)).
9. **Offline-ядро — существующая ценность, а не часть редизайна.** Новые экраны должны читать тот же cache и вызывать те же mutations; sync, файлы, конфликты, курсоры и SQLCipher не переписываются ([useCachedEntities:6](../mobile/src/shared/hooks/useCachedEntities.ts#L6), [mutations:10](../mobile/src/shared/storage/mutations.ts#L10), [архитектура:175](MOBILE_APP_ARCHITECTURE.md#L175)).
10. **Эталоны разных дат противоречат друг другу.** Старые макеты показывают «Финансы» внизу и сегменты над списком; текущий `MobileBottomNav` уже другой, а переключателя «Предстоящие / Прошедшие» в runtime-компонентах нет. `design-qa.md` фиксирует 40 px и `#C75F00`, текущий CSS — 36 px и `#9a6b27`. Различия разобраны ниже, без подмены фактов ([макет:207](mockups/events-segment-switch.html#L207), [QA:66](../design-qa.md#L66), [CSS:483](../app/globals.css#L483)).

## 3. Карта навигации и целевое поведение

| Слот | Сейчас Android | PWA / целевое Android-представление |
|---|---|---|
| 1 | Главная (`index`) | **Важное**; переработать содержимое существующего `index`, не терять состояние sync. Бейдж просроченных задач, не сумма всех метрик. |
| 2 | Мероприятия | **Мероприятия / Заказы** из resolver; тап открывает подменю «Предстоящие / Прошедшие», выбор устанавливает scope и открывает `events`. |
| 3 | Клиенты | **+**, действие, а не шестой экран или вкладка с пустым содержимым. |
| 4 | Финансы | **Клиенты**, прямой переход. Финансы остаются route `/(tabs)/finance`, но убираются из видимых tab slots и появляются как «Транзакции» в Меню. |
| 5 | Ещё | **Меню**, overlay с аккордеоном. `/(tabs)/more` сохраняется как совместимый вход в ту же пользовательскую навигацию, без второго расходящегося каталога. |

PWA-источник: [MobileBottomNav.js:27](../components/MobileBottomNav.js#L27), [46](../components/MobileBottomNav.js#L46), [172](../components/MobileBottomNav.js#L172), [248](../components/MobileBottomNav.js#L248). Одновременно открыта только одна панель. Повторный тап, тап по затемнению, смена маршрута закрывают её; Android Back сначала закрывает overlay, затем действует как навигация. Активность «Меню» определяется текущим дополнительным разделом. Не терять scroll position и фильтры при временном открытии панели.

**Порядок пользовательского Меню**, полученный фильтрацией `MENU_SHEET_GROUP_ORDER=[4,11,7,5,8,9,6,10,12,99]` и `pagesGroups`: «История действий» → «Статистика» → «Транзакции» → «Звонки» → **«Настройки»** → «Обратная связь». Внутри «Настройки»: Общие настройки → Мои услуги → Интеграции → Импорт и экспорт → Документы → Списки → Уведомления → Реферальная система. Группы 8, 10, 99 исключены; группа клиентов после исключения нижнего слота пуста, группа 3 «Услуги» также пуста. Не показывать пустые заголовки.

Группа с двумя и более пунктами — аккордеон, по умолчанию закрыт; одиночная — сразу строка. Панель прокручивается до 62% высоты доступного окна, выше нижней навигации. Непрочитанная поддержка получает `99+`, как PWA ([строки меню:73](../components/MobileBottomNav.js#L73)), а не `!`, как сейчас Android. Профиль и тариф не входят в `pages`; сохранить отдельные личные входы из текущего `more`, разместив их в компактной верхней части native-панели или её служебной области. **Это предложение адаптации**, не утверждение о наличии этих строк в PWA-шторке. Общий `Notice`-аналог с success/warning/error/info/neutral строится на проверенных цветах, без произвольных светлых блоков в dark theme.

### 5.6. «Важное»

`AttentionContent` — только оболочка; реальная фактура в [upcomingEventsOverviewFunc.js:551](../layouts/modals/modalsFunc/upcomingEventsOverviewFunc.js#L551). Последовательность текущего runtime:

1. `FirstRequestPrompt` перед обзором; затем горизонтальная summary-лента ненулевых счётчиков: просрочено, сегодня, завтра, сообщения, не закрыто, даты клиентов. Тап прокручивает к секции, не открывает отдельный экран задач.
2. Условное «Закрытие мероприятий» при `pastClosableCount > 0`: пояснение и переход к прошедшим с фильтром незакрытых. **Нет массового закрытия одним нажатием** — текущая кнопка только навигационная ([479](../layouts/modals/modalsFunc/upcomingEventsOverviewFunc.js#L479)).
3. «Просрочено / Сегодня / Завтра» с pending-count и текстом даже пустой секции. В просроченные дополнительно входят просроченные задатки. Карточка задачи: заголовок/дата, контекст работы и адрес, отметка/отмена выполнения, редактирование/удаление, быстрый перенос. Использовать сегментные действия из существующей логики PWA, не всегда одинаковые `+1/+3/сейчас`.
4. Выполненные располагаются после невыполненных, не увеличивают pending-count. Текущий код сохраняет done с сегодняшней/завтрашней датой; done с просроченной датой — только выполненные сегодня; без срока или позднее — только выполненные сегодня и в секции «Сегодня» ([200](../layouts/modals/modalsFunc/upcomingEventsOverviewFunc.js#L200)). Это точнее упрощённого описания «все выполненные сегодня переезжают в Сегодня».
5. Неотвеченные сообщения: avatar-initial, клиент/канал/время, превью, unread, переход к диалогу. Это online-данные, не новый постоянный store сообщений. Telegram/WhatsApp в иллюстрации не доказывают поддержку этих провайдеров существующим mobile API.
6. Sync-секция, если есть очередь: сеть, pending/ready/failed/conflict, retry и переход к подробностям. Native может использовать более полный существующий `useSyncRunState` — не копировать web-очередь.
7. Работы на 3 дня: сейчас PWA использует полноценный `EventCard`, а не маленькую карточку-календарик из макета ([948](../layouts/modals/modalsFunc/upcomingEventsOverviewFunc.js#L948)). Затем значимые даты клиентов при наличии — название, клиент, комментарий, дата и оставшиеся дни, переход в клиента.

В обзоре текущий web JSX ограничивает вывод ряда секций первыми 12; счётчик отражает весь набор. Для Android требуется такой же предсказуемый доступ к остальным записям, без потери задач; способ «показать все» фиксировать как native-адаптацию. Пункт roadmap «заявки без следующего шага» ([469](ROADMAP.md#L469)) не объявлять существующим блоком: соответствующего UI в прочитанном overview нет, отдельное продуктовое расширение сюда не включается.

### 5.7. Просмотр и форма работы

PWA-просмотр ([eventViewFunc:576](../layouts/modals/modalsFunc/eventViewFunc.js#L576)): notice импорта/галерея при наличии → tags/actions → адрес, дата создания и status → начало/окончание/длительность → описание → предупреждение обязательств → финансы для не-draft (договор/получено/расходы/итог) → подробности → контакты → задачи → навигация. Native сейчас начинает с клиента, затем детали и услуги, контакты/задачи и длинная группа кнопок ([events detail:50](../mobile/app/events/[id].tsx#L50)). Сохранить преимущества native маршрутов, но согласовать hierarchy и открыть редактирование нужной секции из overflow.

Основные вкладки редактора PWA: **Общие → Клиент и Контакты → Финансы и Документы** ([eventFunc:1654](../layouts/modals/modalsFunc/eventFunc.js#L1654), [1858](../layouts/modals/modalsFunc/eventFunc.js#L1858), [2033](../layouts/modals/modalsFunc/eventFunc.js#L2033)). Общие: AI/статус, тип/услуги, даты, локация, описание, опциональная передача/проверка импорта, дата заявки. Контакты: основной клиент, дополнительные контакты, задачи с фильтром выполненных. Финансы: договорная сумма, ожидание/сумма/дата задатка, комментарий, договорность, документы/предложения и транзакции. Native-форма должна сохранять введённое при смене вкладки, Back/keyboard, failed-save; не запускать mutation до явного сохранения. HTML rich text web не выводить в native как сырые теги. Коммерческие предложения, адресные подсказки и закрытие с причинами блокировки требуют отдельной проверки доступных API; наличие полей Event не доказывает наличие native-сценария.

### 6.1. Общие границы каждого захода

Каждая строка ниже — отдельный рабочий заход с одним проверяемым результатом; не объединять несколько строк в «общий редизайн». Новые предложенные файлы явно помечены `новый`. Для **каждого** этапа обязательны `cd mobile && npm run typecheck` и `cd mobile && npm test` (далее **T**). ### 6.3. Контрактные пробелы, которые нельзя скрыть пунктом «полировка»

- **Settings:** нынешний [mobile terminology PUT:17](../app/api/mobile/v1/settings/terminology/route.js#L17) записывает только `primaryEntityTerminology`. Наличие `timeZone` в чтении ещё не даёт права сохранять его этим PUT. Перед W проверить существующие узкие bearer-маршруты для длительности/передачи/часового пояса; если их нет, серверная работа за пределами этого плана, функция остаётся незакрытой.
- **Импорт:** файловый API уже использует [getRequestContext:64](../server/fileImportService.js#L64); это позволяет планировать native-adapter, но не заменяет staging smoke. [file-import GET:31](../app/api/events/file-import/route.js#L31) возвращает tenant jobs, [POST по id:14](../app/api/events/file-import/[id]/route.js#L14) меняет job. В AC/AD повторно прочитать весь state/action-контракт, стоимость и ограничения файла. Google import — отдельный контракт от синхронизации.
- **Экспорт:** PWA экспортирует три набора и требует `allowStatistics` ([ExportContent:25](../layouts/content/ExportContent.js#L25)); Android-CSV статистики не обеспечивает этого. Сначала сравнить поля и полноту, включая все страницы; не назвать частичный local cache «все данные».
- **Telegram Business:** web endpoints есть ([status:36](../app/api/integrations/telegram/status/route.js#L36)), native список/диалоги сейчас Avito/VK. Нужна проверка минимизации payload, bearer, тарифов, провайдеров переписок и summary; не рисовать неработающий Telegram в Важном по иллюстрации.
- **Предложения/расширенные документы и адресные подсказки:** наличие web-вкладки не доказывает mobile API/формат для native. В N–Q/X перечислить подтверждённые операции и отдельные неподдержанные сценарии. Web-ссылка может быть временной альтернативой, но должна быть явно названа и не учитывается как завершённый паритет.
- **Роль dev:** удалить privileged UI можно в B/C, но превратить developer bearer в обычного пользователя на клиенте нельзя. Решение §7 предотвращает непреднамеренные глобальные запросы без изменения сервера.

## 8. Риски, открытые вопросы и проверка

### 8.1. Фактические ограничения среды

В этой сессии `uname -m` дал `aarch64`; `command -v adb` и `command -v java` не нашли исполняемые файлы. Это подтверждает отсутствие этих инструментов в PATH на текущем Orange Pi, не отсутствие Android SDK на любой машине владельца. ### 8.3. Открытые решения и рабочие допущения

| Вопрос | Рабочее решение плана / что нужно подтвердить |
|---|---|
| Runtime или старые макеты при конфликте? | Базовый эталон — текущий JSX/CSS с явными исключениями §4.1. Если нужны именно старые 40 px/бронза, владелец должен выбрать это как отдельное изменение дизайна, не «исправление паритета». |
| Нужны ли сегменты сверху одновременно с нижним подменю? | Runtime-first: нижнее подменю обязательно, верхние сегменты не включены по умолчанию. Для макетного варианта достаточно решения владельца; нет необходимости останавливать остальные этапы. |
| Как dev использует собственную CRM и поддержку? | CRM остаётся, operator-возможности удаляются; поддержку для dev закрыть до user-scoped контракта (§7). Уточнить необходимость личной поддержки именно под dev-аккаунтом. |
| Где профиль/тариф/sync после удаления «Ещё» как страницы меню? | Сохранить компактные личные входы в native-панели и sync на Важном. Их точное место — адаптация, поскольку web `pages` не содержит этих пунктов. |
| Font/gradient fidelity без новых бинарных assets? | Проверить возможность использовать имеющиеся файлы шрифтов и средства native rendering. Системный шрифт/плоский фон — только явно согласованное приближение; pixel-perfect пока не подтверждён. |
| Settings/import/Telegram/предложения требуют backend? | Сначала сверить существующие bearer-контракты; известные ограничения §6.3. В рамках Android-only плана нет разрешения дописывать сервер. Не закрывать функциональный gap ссылкой «откройте web». |
| Семантика прошедших, суммы и done? | Написать сравнительные fixtures с фиксированным now; различать `dateEnd`, вычисленный finished, closed, транзакции-обязательства и doneAt. Визуальный перенос не должен вводить новую бизнес-логику без фиксации. |
| Поступают ли новые поля в mobile cache? | Проверять mobile types, sanitize/serializers и sync payload чтением. Если поля отсутствуют, UI не выдумывает значение и не меняет SQLCipher schema ради карточки. |
| Как оценивать недоступные online-секции? | Явные loading/offline/error/retry; не заменять незагруженные данные пустым успешным состоянием и не запускать ненужный постоянный polling. |
| Какие Android-девайсы/версии доступны для QA? | Уточнить у владельца. Основной аппарат + второе устройство для sync/tenant, gesture/button navigation и увеличенный текст; исторический Samsung из roadmap не означает его доступность сейчас. |

### 8.4. Минимальная сквозная приёмка на устройстве

1. Открыть Важное из cold start; проверить summary/pending/done, работу Back и Меню; перейти к Предстоящим/Прошедшим и Транзакциям. У dev/admin нет платформенных разделов/запросов.
2. В авиарежиме создать клиента в разделе «Клиенты», через «+» создать заявку, изменить контакты/даты/услуги, добавить задачу и транзакцию через соответствующие формы. Перезапустить приложение: данные/очередь сохранены. После сети дождаться штатного sync и сверить web на том же tenant; дублей нет.
3. Два устройства: конфликт изменения, выбор локального/серверного, tombstone после удаления, failed file retry; UI не скрывает ошибки и не выдаёт pending за success. Использовать существующие `maestro/sync-conflict.yaml`, `sync-queue-retry.yaml`, `database-health.yaml`.
4. Выполнить/отменить/перенести задачу на Важном, проверить счетчики и видимость doneAt сегодня; отдельно оплаченный и просроченный задаток, незакрытая многодневная работа, дата клиента на границе года.
5. Проверить четыре сценария создания, тариф без ИИ, отказ микрофона/сеть/отмена. AI не сохраняет работу без подтверждения и не подменяет клиента чужим ID.
6. Открыть карточку из обоих schemes, пуша и OAuth возврата при открытом приложении и cold start; после auth/onboarding не потерять назначение. Проверить старые finance/tasks/more ссылки.
7. На тех же fixture данных сравнить PWA и APK в light/dark: карточки/фильтры/поиск/пустые состояния/шторки; длинные заголовки/суммы, 320 px и увеличенный текст. Контакты и footer не обрезаны, overlay не двигает список, клавиатура не закрывает сохранение.
8. Для online-only функций использовать тестовые tenants: чужие client/event/file/support IDs и недоступный тариф не дают доступа; secrets не появляются в логах/screenshots/cache. Отдельно системные picker/share, push denied/granted и background/resume.

Для каждого прогона фиксировать версию и build ID, устройство/Android, тему/font scale, состояние сети, fixture и результат. Пока нет такого доказательства, статус — «код реализован, device QA не выполнен», а не «паритет завершён». Этот документ завершает только этап A; реализация, EAS/device QA и закрытие M1-T7 — последующие работы.
