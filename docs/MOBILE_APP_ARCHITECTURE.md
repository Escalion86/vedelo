# Mobile App Architecture (React Native + Expo)

## Цель

- Запустить полноценное мобильное приложение Ведело для сценариев:
  - быстрый контроль заявок и перезвонов;
  - надежные push-напоминания;
  - работа по мероприятиям и задаткам в 1-2 тапа;
  - переход из уведомления сразу в нужную карточку.

---

## Принципы

- Mobile-first UX: основной пользователь работает с телефона.
- Backend-first: мобильное приложение использует существующий API проекта.
- Полный пользовательский Android 1.0 с последующим нативным расширением 1.1 без переписывания ядра.
- Единые бизнес-правила между web и mobile.
- Offline-first для критичных сценариев (создание/изменение заявки и задач контакта).

---

## Стек (реализуемый)

- Expo SDK 55 + prebuild/EAS development build
- React Native
- Expo Router (навигация)
- TanStack Query (кэш/синхронизация API)
- SQLCipher через `expo-sqlite` (локальные сущности, outbox, конфликты и курсоры)
- expo-notifications (push-уведомления)
- expo-linking (deep links)
- expo-secure-store (хранение токенов)
- react-hook-form + zod (формы/валидация)

## Auth и безопасность

- Web продолжает использовать NextAuth cookie, Android использует короткий JWT access token и ротируемый случайный refresh token.
- На сервере refresh token хранится только в виде SHA-256 хеша; каждая установка имеет отдельную отзывную сессию.
- Ротация refresh token выполняется атомарным compare-and-swap по предыдущему хешу: из конкурентных запросов успешен только один, а старый token сразу перестаёт действовать.
- Каждый mobile access token содержит ID сессии; bearer-авторизация дополнительно проверяет, что эта сессия принадлежит пользователю, не отозвана и не истекла. Отзыв устройства, смена/восстановление пароля и удаление аккаунта тем самым прекращают доступ без ожидания истечения JWT.
- Android очищает локальную сессию только после подтверждённого `401` от refresh endpoint либо если refresh token отсутствует. Сетевой сбой, rate limit и `5xx` сохраняют токены, зашифрованный cache и outbox для следующей попытки. Конкурентные `401` всех экранов объединяются в одну ротацию, после которой каждый исходный запрос повторяется не более одного раза.
- `auth/sessions` возвращает явную безопасную модель устройства без `deviceId`, tenant и token hash: название/платформа, версия приложения, даты создания, активности и истечения, признак текущей сессии. Текущее устройство отключается только через logout; отзыв другого устройства одновременно прекращает bearer-доступ и деактивирует его Expo push token.
- Offline logout немедленно очищает локальную сессию, SQLCipher и push-настройку, а текущий refresh token временно сохраняет в отдельной записи SecureStore. При старте или восстановлении сети Android повторяет logout без access token; сервер находит только соответствующую сессию по SHA-256 хешу refresh token, отзывает её и деактивирует push её `tenantId + deviceId`. Успешный и повторный logout возвращают одинаковый безопасный ответ.
- VK ID использует PKCE и разделяет мобильные режимы: `login` не создаёт неизвестный аккаунт, а `register` требует отдельных действий для Пользовательского соглашения, ознакомления с Политикой и согласия на обработку персональных данных до создания пользователя.
- Восстановление по подтверждённому звонку или SMS меняет пароль, отзывает все прежние mobile-сессии и только затем создаёт новую сессию текущего устройства.
- Access/refresh token и ключ SQLCipher хранятся в `SecureStore` с доступом только на текущем устройстве.
- Автовыход при 401 + редирект на login.
- Минимизация персональных данных в локальном кэше.

## API-контракт `/api/mobile/v1`

- `auth/login|register|recovery|refresh|logout|vk|me|sessions|delete-account`
- `onboarding`, `profile/requisites`, `files`, `tasks/action`, `notifications`, `notifications/test`
- `document-templates`, `document-templates/[id]`
- `events/[id]/documents/generate`
- `integrations/status`, `integrations/[provider]` для Avito/VK, `integrations/google-calendar[/auth-url|/calendars|/select]`
- `conversations/[provider]`, `conversations/[provider]/[id]`, `conversations/[provider]/[id]/messages`
- `bootstrap`
- `sync/pull`, `sync/push`
- `events`, `clients`, `transactions`, `services`, `service-groups`, `calls`, `statistics`, `referrals`
- `clients/[id]/merge` — online-only preview и необратимое объединение синхронизированных дублей
- `lists` — безопасное online-редактирование городов, города по умолчанию и типов мероприятий без передачи остальных `SiteSettings.custom`
- `bootstrap.access` содержит только булевы тарифные возможности и числовой лимит мероприятий. Вложенные модели пользователя/тарифа, цены, пароль, OAuth-токены и другие внутренние поля в mobile payload не попадают.
- Единый формат ошибок:

```json
{
  "success": false,
  "error": {
    "code": "SOME_CODE",
    "type": "validation|auth|rate_limit|unknown",
    "message": "Текст ошибки"
  }
}
```

## Пользовательские интеграции

- Экран `Ещё → Интеграции` получает только доступность, подключённость и безопасный статус Google Calendar, Avito, VK, Novofon, AITunnel и Public Leads API.
- Секреты, access token, webhook token и полные provider payload мобильному клиенту не передаются и локально не кэшируются.
- Google Calendar подключается из Android через системную OAuth-сессию. Подписанный state действует 10 минут, привязан к конкретным user/tenant/mobile session, хранится на сервере только как SHA-256 hash и атомарно удаляется до обмена кода, поэтому callback нельзя повторить.
- После возврата в `vedelo://more/integrations` пользователь выбирает доступный календарь, включает или приостанавливает синхронизацию, задаёт напоминание и поведение отменённых/переданных событий. Development build использует `vedelo-dev://`, а legacy-схемы `artistcrm://` и `artistcrm-dev://` продолжают приниматься. Отключение удаляет OAuth credentials, email, sync token и выбранный календарь на сервере.
- Avito и VK подключаются online-only из Android: реквизиты живут только в памяти открытой формы, передаются один раз по bearer TLS-запросу и сразу очищаются после ответа. Они не записываются в SecureStore, SQLite или query cache.
- `integrations/[provider]` возвращает только безопасный статус, публичный ID аккаунта и даты диагностики. Client secret Avito, access token/confirmation VK, webhook URL/token/secret и полный `SiteSettings.custom` никогда не входят в mobile JSON; отключение очищает эти значения на сервере даже при последующей потере тарифного доступа.
- Novofon подключается выпуском нового случайного webhook secret на сервере. Secret и готовый URL возвращаются Android только в ответе выпуска, живут в памяти открытой формы и после закрытия больше не доступны; повторный выпуск немедленно инвалидирует старый URL. Ключ API Novofon в обычном статусе заменён булевым `hasApiKey`.
- Ключ AITunnel вводится в защищённое поле, после online-сохранения очищается, а Android получает только `configured`, состояние паузы и названия моделей распознавания/анализа. Отключение удаляет ключ и provider-настройки на сервере.
- Public Leads API создаёт отдельный криптографически случайный ключ для каждого источника. Полный ключ возвращается ровно в ответе создания, далее список содержит только ID, название, активность и последние четыре символа; доступны пауза всего endpoint, включение/отключение и удаление отдельных ключей. Отключение интеграции удаляет все ключи.
- Кнопка копирования помещает одноразовый секрет в системный Android clipboard только по явному действию пользователя. Ведело не пишет его в SQLCipher, SecureStore, AsyncStorage или query cache.
- Списки и история переписок Avito/VK доступны online-only; открыть их можно из раздела интеграций, клиента или мероприятия. В диалоге доступны ответ, отметка прочитанного и статусы `В работе / Закрыт / Игнорируется`.
- Мобильный контракт сериализует только нужные поля диалога и сообщения, исключая `tenantId`, provider ID и `raw`.
- Отправка ответа и отметка прочитанного используют те же tenant-aware и тарифные правила, что web, через общий bearer/cookie request context.
- Адреса API Avito и VK задаются только в server runtime (`AVITO_API_BASE_URL`, `VK_API_BASE_URL`); production использует официальные API, а изолированные HTTP-тесты подменяют upstream без передачи этой конфигурации мобильному приложению.

## Профиль и реквизиты артиста

- Android редактирует имя, фамилию, отчество, email, WhatsApp, Viber, Telegram, VK и Instagram через узкий `auth/me`. Сервер нормализует строки/телефоны и игнорирует попытки изменить `tenantId`, роль, пароль или другие служебные поля.
- Безопасная модель текущего пользователя возвращает эти контакты, но не содержит password hash, OAuth credentials, уведомления и внутренние настройки.
- `profile/requisites` читает и обновляет только поля `contractArtist*`, используемые генерацией договора и акта: статус ИП/самозанятого, ФИО, наименование, ОГРНИП, ИНН, банк, БИК, счета и юридический адрес.
- При выборе самозанятого ОГРНИП очищается. Числовые реквизиты нормализуются, остальные значения `SiteSettings.custom`, включая секреты интеграций, никогда не входят в ответ и не могут быть изменены этим endpoint.
- Профиль и реквизиты являются online-only персональными настройками; локальный offline CRUD клиентов остаётся отдельным контуром.

## Клиенты

- Основные контакты, тип, приоритетный канал, комментарий, значимые даты и реквизиты редактируются offline-first и проходят через общий outbox.
- Карточка клиента собирает из локального кэша его основные/дополнительные мероприятия и связанные транзакции, поэтому история доступна без сети.
- Объединение дублей выполняется только online и только для синхронизированных клиентов: перед подтверждением сервер считает переносимые мероприятия, транзакции, переписки и звонки.
- После объединения сервер повышает `syncVersion` связанных offline-сущностей и создаёт tombstone удалённого дубля; mobile v1 не передаёт в preview tenant ID, пароль и внутренние настройки контакта.

## Финансы

- Транзакции создаются и редактируются offline-first, могут быть связаны с клиентом и активным мероприятием; локальные ID зависимостей заменяются sync-движком до отправки.
- Мобильный редактор использует каноничные категории доходов/расходов и методы оплаты web-приложения. Для обязательства дата считается плановой.
- Обязательства отображаются отдельно и не входят в фактические доходы, расходы и результат до смены метода оплаты; при исполнении обязательства пользователь обязан указать фактическую дату.
- Контроль договора учитывает только клиентские оплаты `deposit/final_payment` и их legacy-аналоги, поэтому чаевые и реферальные выплаты не уменьшают остаток.
- Контроль задатка показывает неоплаченную сумму или отдельный статус, если ожидаемая сумма не заполнена.

## Услуги и пользовательские списки

- Услуги и группы услуг входят в offline sync: услуга сохраняет `groupId`, а локальная группа может использоваться до получения серверного ID.
- Перед удалением группы Android локально переносит её услуги в «Без группы»; сервер также повышает их `syncVersion`, чтобы изменение пришло на другие устройства.
- Города, основной город и типы мероприятий редактируются online-only через узкий mobile v1 endpoint и сохраняются в зашифрованный `siteSettings` cache для офлайн-подсказок.
- Mobile API обновляет только `towns`, `defaultTown` и `custom.eventTypes`; токены интеграций, DOCX-шаблоны и другие значения `custom` не принимаются и не возвращаются.
- Новая форма мероприятия подставляет основной город и предлагает сохранённые города/типы без обязательного подключения к сети.

## Календарь мероприятий

- Экран `Мероприятия` переключается между списком и локальным month-view без отдельного сетевого запроса.
- Месячная сетка строится с понедельника и всегда содержит шесть недель, поэтому высота календаря не меняется при навигации.
- Счётчик дня объединяет дату мероприятия и его `additionalEvents`; выбор записи открывает связанную карточку мероприятия.
- Значения формата `YYYY-MM-DD` разбираются в локальной временной зоне, чтобы календарный день не смещался из-за UTC.
- Заявки без даты явно подсчитываются в календаре и остаются доступны в режиме списка.

### Адрес и навигация

- Android сохраняет город, улицу, дом, подъезд, этаж, офис/квартиру и комментарий к площадке в общем `event.address`.
- Карточка формирует безопасные ссылки поиска для 2ГИС и Яндекс Карт; сохранённые ссылки принимаются только со схемами `https/http`, `dgis` или `yandexnavi`.
- Адрес кодируется как поисковый запрос, поэтому кириллица, пробелы и дробные номера домов не ломают intent.

### Голосовой AI-черновик

- Android записывает голос только после явного нажатия пользователя и запроса `RECORD_AUDIO`; фоновая запись отключена конфигурацией Expo Audio.
- Запись ограничена двумя минутами, отправляется online-only через bearer endpoint `/api/mobile/v1/events/voice-transcript` и удаляется из cache после успеха или ошибки.
- Расшифровка передаётся `/api/mobile/v1/events/ai-draft`; оба маршрута используют общий cookie/bearer request context и серверную тарифную проверку `allowAi`.
- Перед применением пользователь видит редактируемую расшифровку и число найденных полей. AI не перезаписывает форму без отдельного подтверждения.
- Клиент из AI-ответа применяется только если его ID уже присутствует в tenant-scoped локальном кэше; неизвестные ID, невалидные даты и суммы игнорируются.
- Ручной текст доступен без разрешения микрофона, но так же требует сети и доступного AI-тарифа.

## Статистика и экспорт

- Экран статистики загружает вычисляемые данные online-only с тарифной и tenant-aware проверкой.
- Доступны фильтры по году, городу и вычисляемому статусу мероприятия, финансовый результат, маржа, остатки к оплате, налоги/комиссии и топ расходов/мероприятий.
- CSV формируется на устройстве из безопасного mobile v1 payload, отправляется через системный share sheet и удаляется из временного каталога после завершения.
- Mobile v1 не выдаёт этому экрану документы, реквизиты, телефоны, `raw` и иные поля, не нужные для расчёта или экспорта.

## Уведомления и deep links

### Push-уведомления

- Типы:
  - просроченный перезвон;
  - событие скоро, задаток не получен;
  - напоминание по подготовке документов.
- Данные уведомления должны содержать:
  - `type`
  - `entityId`
  - `route` (например `event/123`)
- Для задач сервер передаёт `eventId`, `taskId` и категорию `task-actions`.
- Android показывает действия `Выполнено`, `На завтра`, `Через 3 дня`; изменение выполняет tenant-aware `/api/mobile/v1/tasks/action` и при необходимости обновляет Google Calendar.
- Разрешение Android запрашивается только после явного действия пользователя `Включить push`; выбор и последний Expo token хранятся в SecureStore.
- Expo device-token listener обрабатывает ротацию FCM token и заменяет локальный Expo token только после подтверждённой регистрации. Сервер сначала активирует новый token, затем деактивирует остальные активные token того же `tenantId + deviceId`, не затрагивая другие устройства.
- Явное `Отключить push` применяется локально сразу. Если сети нет, старый token остаётся в отдельной SecureStore-очереди только для повторной `/push/expo/unsubscribe`; retry выполняется при foreground и восстановлении сети. Очередь удаляется после подтверждения API и не может удалить новый token, если пользователь успел повторно включить push. Серверная отписка требует совпадения tenant, token и `x-device-id`.
- Отключение деактивирует Expo token только текущего устройства. Ежедневную сводку и её время пользователь настраивает отдельно, с шагом 15 минут.
- Logout и удалённый отзыв mobile session также деактивируют Expo token соответствующего устройства; локальное согласие очищается при выходе.
- Новые API-заявки, готовые записи звонков и ежедневные сводки отправляются одновременно в доступные Web Push и Android Expo Push каналы.

### Deep links

- Основная схема: `vedelo://event/:id`, `vedelo://lead/:id`; `artistcrm://` сохраняется для старых ссылок.
- При тапе по уведомлению:
  - открыть приложение;
  - перейти на конкретную карточку.

## Виджеты и звонки (важные ограничения)

### Виджеты

- Home widget входит в Android 1.1+ и будет реализован Kotlin-модулем поверх prebuild.

### Звонки

- Android 1.0: серверный журнал IP-телефонии, карточка записи/расшифровки/AI-анализа, привязка к клиенту и мероприятию, системный `tel:` intent и быстрый результат звонка.
- Результаты `Ответил / Не ответил / Перезвонить / Создать задачу` сохраняются в звонке. Следующий контакт добавляется только в tenant-связанное мероприятие и best-effort синхронизируется с Google Calendar.
- Mobile v1 не передаёт Android внутренний ID звонка провайдера, storage key записи, tenant ID и необработанный provider payload.
- Android 1.1: `CallScreeningService` и роль `ROLE_CALL_SCREENING`, без `READ_CALL_LOG` и произвольного overlay-разрешения.
- Caller ID ищет номер только в минимальном локальном зашифрованном индексе и должен ответить Android быстрее пяти секунд.

## Offline и синхронизация

- Реализован зашифрованный read-through cache и outbox с retry/backoff.
- Синхронизация запускается при старте, возврате в приложение, восстановлении сети, вручную и best-effort background task. Фоновая задача проверяет наличие сохранённой mobile-сессии до доступа к данным, регистрируется только после авторизации и снимается при logout. Экран синхронизации показывает, зарегистрирована ли задача или её ограничил Android; точное время запуска всегда определяет система.
- Конфликты хранят `base/local/remote/remoteVersion` и разрешаются пользователем по каждому полю.

### Обязательный offline-сценарий (must-have)

- Если сети нет, создание заявки НЕ должно падать ошибкой для пользователя.
- Действие сохраняется локально в `outbox` со статусом `pending`.
- В UI заявка помечается как `Ожидает синхронизации`.
- При восстановлении сети запускается авто-синхронизация:
  - отправка операций из outbox по порядку;
  - после создания локальной сущности её `local-*` ID заменяется серверным ID во всех ожидающих payload и связанных записях кэша до отправки следующей операции;
  - после успешной отправки статус `synced`;
  - при ошибке валидации статус `failed` + возможность вручную исправить и повторить.
- Прерванная при закрытии приложения операция `syncing` возвращается в retry-очередь при следующем открытии базы.
- `sync/pull` использует постраничный непрозрачный cursor с отдельными позициями `updatedAt + _id` для каждой сущности и tombstones. Верхняя граница фиксируется на первой странице, поэтому backlog больше 2000 записей дочитывается без пропусков и без захвата новых изменений посередине snapshot.
- Android применяет сущности всех страниц идемпотентно, но сохраняет итоговый cursor и применяет tombstones только после успешного завершения snapshot. Авария посередине приводит к безопасному повторному чтению, а не к потере удаления или частично сдвинутому cursor.

### Локальное хранилище

- SQLCipher `artistcrm.db`; ключ создаётся на устройстве и хранится в Android Keystore через SecureStore.
- После `PRAGMA key` приложение проверяет `PRAGMA cipher_version` и прекращает инициализацию, если нативная сборка не содержит SQLCipher. Это исключает незаметное создание plaintext SQLite при запуске через несовместимую native-сборку.
- Схема базы версионируется через `PRAGMA user_version`. Каждая версия выполняется отдельной транзакцией, а номер меняется последней командой после успешных DDL. Миграция `1 → 2` добавляет недостающие поля файловой очереди и индекс без пересоздания таблиц; `2 → 3` добавляет персистентное состояние sync-run. Unversioned базы ранних Android-сборок проходят тот же последовательный путь с сохранением cache/outbox/conflicts/cursors.
- Восстановление зависших `syncing/uploading` после process death выполняется одной транзакцией уже после миграций, поэтому частично обновлённая схема не начинает синхронизацию.
- Экран `Синхронизация` получает отдельный read-only снимок здоровья базы: наличие SQLCipher, `user_version`, число кэшированных сущностей, конфликтов и элементов очередей, а также количество `syncing/uploading`, восстановленных при текущем запуске. Диагностика намеренно не возвращает версию библиотеки шифрования, ключ, tenant/entity ID, пути файлов или payload.
- На том же экране пользователь видит каждый активный outbox-элемент и файл: понятное действие/название сущности, статус, безопасно нормализованную ошибку и отдельный retry для `failed`. Проекция outbox не выбирает `payload`, `base_values` и `attachments`, а файловая проекция — `local_uri` и `remote_path`; технические ошибки, URL и токены не выводятся. Retry атомарно переводит только выбранную запись в `pending`, сбрасывая её attempts/backoff перед общим sync.
- Таблица `sync_state` хранит единый результат ручного, foreground и background цикла: `never/pending/syncing/success/attention/offline/failed/interrupted`, времена последней попытки/завершения/полного успеха, агрегат failed/conflict элементов и число последовательных сбоев. Сырой `Error.message`, provider response и stack trace не записываются — только категория `network/auth/rate_limit/server/interrupted/unknown`. Главная подписывается на это состояние и ведёт пользователя в подробную очередь; оставшийся после process death `syncing` атомарно становится `interrupted` вместе с восстановлением outbox/files.
- Новая outbox-операция, локальный файл и ручной retry сразу выставляют `pending`, не перетирая уже идущий `syncing`. Завершение online-цикла одним SQLite `WITH … UPDATE` вычисляет `attention/pending/success` непосредственно из актуальных outbox/file_queue. Поэтому enqueue до финального statement будет замечен им, а enqueue после statement самостоятельно вернёт `pending`; окна для ложного `success` нет. Удаление отменённой локальной операции и окончательное разрешение конфликта пересчитывают состояние очереди.
- Таблицы: `entity_cache`, `outbox`, `sync_conflicts`, `sync_cursors`, `file_queue`, `sync_state`.
- Вложения до 5 МБ шифруются AES-256-GCM в app-private каталоге, расшифровываются только во временный файл перед отправкой и имеют видимый статус очереди.
- Очередь event-вложений хранит `entityType/entityId/attachmentKind`. После получения серверного ID локальная ссылка переписывается до upload, поэтому файл прикрепляется к правильному мероприятию.
- `/api/mobile/v1/events/[id]/files` проверяет bearer tenant, тариф и статус мероприятия, загружает файл в серверный tenant/event-каталог и добавляет `documentFiles` одним запросом. `fileQueueId` сохраняется как закрытый ключ идемпотентности: replay после потери ответа не отправляет файл повторно и не создаёт дубль.
- Пустые файлы отклоняются до шифрования, а ответ upload без URL переводит элемент в ошибку. Автоматический retry ограничен восемью попытками; явный повтор сбрасывает backoff только для выбранного мероприятия и не запускает чужие вложения.
- Конфликт блокирует исходную операцию целиком, поэтому Android хранит её полный patch до решения всех спорных полей. Серверный выбор удаляет только выбранное поле, локальный — перебазирует его на `remoteVersion`; остальные локальные изменения и вложения попадают в один новый outbox-элемент. Конкретный конфликт удаляется атомарно, защищая повтор от двойного нажатия.
- Файловая очередь обрабатывает элементы независимо с exponential backoff и лимитом 8 попыток. Потерянный encrypted blob получает понятную ошибку и не блокирует следующие файлы, обычный outbox или последующий pull.
- Статус `uploading`, оставшийся после process death, при открытии базы переводится в немедленно повторяемый `failed`. Расшифрованные upload/share-копии удаляются в `finally`, а осиротевшие временные файлы с системным префиксом очищаются при следующем запуске sync.
- Mobile upload принимает ровно один непустой файл размером до 5 МБ. Имя очищается сервером, а каталог `artistcrm/<tenantId>/mobile` строится только из авторизованного tenant context и не принимается от клиента; перед передачей в облачное хранилище bearer-сессия проверяется повторно.
- URL облачного upstream на сервере можно заменить через `ESCALIONCLOUD_API_URL`; production по умолчанию использует EscalionCloud, а HTTP integration запускает локальный mock и проверяет реальный multipart без обращения во внешнюю систему.
- DOCX-шаблоны не попадают целиком в offline bootstrap: список содержит только метаданные, а файл скачивается отдельным авторизованным запросом.
- Генерация договора/акта выполняется online-only на сервере тем же рендерером, что и web, включая таблицы реквизитов. Результат загружается в tenant/event каталог и добавляется в `event.documents`.

### Технический контракт для sync

- Каждая офлайн-операция имеет:
  - `operationId` (uuid)
  - `entityType`
  - `entityLocalId`
  - `payload`
  - `createdAt`
  - `attempts`
  - `status` (`pending|syncing|failed|synced`)
- Серверные endpoint'ы для create/update должны поддерживать идемпотентность:
  - заголовок `Idempotency-Key` или поле `operationId`.
  - scope ключа — `tenantId + operationId`; одинаковый UUID в разных tenant не пересекается;
  - сервер хранит стабильный SHA-256 отпечаток содержимого операции и отклоняет повторное использование UUID с другим payload;
  - перед CRUD создаётся уникальная резервация `reserved`, затем фаза меняется на `applying`, а ответ фиксируется как `completed`;
  - параллельный повтор не выполняет CRUD второй раз; зависшую `reserved`-операцию можно безопасно перехватить, но зависшая `applying` возвращает `OPERATION_STATE_UNKNOWN`, потому что повтор вслепую мог бы создать дубль.
- Tombstone хранится 180 дней, scoped по tenant и повышает version через `$max`, поэтому поздняя повторная запись не может откатить версию удаления.
- Mongo integration-набор запускается командой `npm run test:mobile-server`: при доступном `mongod` он поднимает временную изолированную базу, проверяет реальную гонку уникального индекса, replay/reuse, одинаковый UUID в разных tenant, tombstone, cursor и конкурентную ротацию refresh token с отзывом сессии; при отсутствии бинарника integration-case явно помечается skipped.
- HTTP integration-набор запускается командой `npm run test:mobile-http`: после production build он поднимает временные MongoDB, Next.js и cloud mock, проверяет route handlers авторизации/сессий/файлов, offline logout по refresh token без access token, отзыв bearer/push, CRUD всех пяти offline-типов через `sync/push|pull`, версии, replay, conflict, tombstones между двумя устройствами, tenant isolation и восстановление сохранённых фаз `reserved/applying`, затем удаляет временные данные.
- В той же двух-tenant среде проверяются online-only разделы: bootstrap, задачи, звонки, статистика, рефералы, списки, уведомления, безопасные статусы интеграций и метаданные DOCX-шаблонов; тест дополнительно запрещает появление известных секретов в JSON-ответах.
- Локальные provider mocks Avito/VK принимают реальные исходящие server-запросы: тест проверяет списки и сообщения каждого tenant, запрет cross-tenant чтения, смену статуса и unread-счётчика, отправку ответа, подключение и повторную проверку реквизитов, а также отсутствие `raw`, provider ID, webhook-данных и секретов в mobile JSON. При отключении тест подтверждает полную очистку credentials только текущего tenant.
- HTTP-контур Novofon/AITunnel/Public Leads проверяет выпуск и ротацию webhook, сохранение моделей, паузу AI, создание/отключение/удаление нескольких API-ключей, одноразовую выдачу новых секретов и безопасные последующие GET. Дополнительно подтверждаются tenant isolation, тарифный запрет подключения и возможность удалить серверные credentials после потери тарифного доступа.
- HTTP-контур профиля проверяет нормализацию контактов и реквизитов артиста, повторное чтение безопасной модели, запрет подмены tenant/роли/password и невозможность записать произвольный integration secret через `profile/requisites`.
- Auth provider mocks проверяют полный TelefonIP start/check, SMS webhook и server-side VK ID code exchange с PKCE. HTTP-сценарий создаёт телефонный и VK-аккаунты только после согласий, запрещает неявную VK-регистрацию из режима входа, меняет пароль и подтверждает немедленный отзыв прежней сессии; provider token, SMS-код и OAuth access token в mobile JSON не возвращаются.
- Google OAuth/Calendar mocks проверяют выдачу session-bound state, callback без web-cookie, обмен authorization code, выбор календаря, сохранение настроек, запрет replay и очистку credentials при отключении. Известные client secret, refresh/access token и provider authorization header запрещены в mobile JSON.

### Конфликты

- Сервер сравнивает `baseVersion` и исходные значения изменённых полей.
- Несвязанные изменения проходят автоматически; пересекающиеся выводятся в мобильном диалоге «оставить моё / принять сервер».

## Наблюдаемость и качество

- Перед rollout подключить выбранный владельцем production crash-reporting (например, Sentry) и зафиксировать DSN в EAS secret; без внешнего проекта нельзя подтвердить порог crash-free 99,5%.
- Планируемая аналитика событий:
  - `contact_planned`, `contact_done`, `deposit_marked`, `notification_opened`.
- Тесты:
  - unit: форматтеры/валидация/маппинг API
  - Maestro e2e: login и deep links;
  - Android offline CRUD клиента, заявки и транзакции с явным авиарежимом и восстановлением после process death;
  - принятие серверного значения конфликта и генерация DOCX проверяются отдельными flow на development build с подготовленными серверными фикстурами;
  - системные Document Picker и share sheet проверяются на физическом устройстве с тестовым DOCX в Downloads.

## Риски и решения

- Push-стабильность: обязательно серверный retry и дедупликация.
- Разница платформ: не обещать функционал, запрещенный ОС.
- Нативные риски: Android 1.0 остаётся на Expo prebuild/CNG, Kotlin Caller ID выпускается отдельно в 1.1.
- Offline-конфликты: с первого релиза хранить `operationId` и лог синхронизации, чтобы не терять/не дублировать заявки.
