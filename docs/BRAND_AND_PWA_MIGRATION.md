# Переезд ArtistCRM → «Ведело»

## Что меняется

- Основной бренд и домен: **«Ведело»**, `https://vedelo.ru`.
- В течение шести месяцев в продукте используется подпись «Ведело — ранее ArtistCRM».
- Внутренние API, модели и идентификаторы `events`/`eventId`, MongoDB и package ID `ru.escalion.artistcrm` не меняются.
- PartyCRM не участвует в ребрендинге и продолжает работать на своих маршрутах.

## Перед запуском

Статус проверки 2026-09-14: `vedelo.ru` зарегистрирован, делегирован и вместе с `www.vedelo.ru` разрешается в `5.129.192.130`. HTTPS-проверка пока завершается ошибкой TLS, поэтому публичный запуск до выпуска и подключения сертификата заблокирован. Анонимный запрос «Ведело» в официальной поисковой платформе Роспатента вернул `401`; проверку по МКТУ 9, 35 и 42 нужно повторить после восстановления публичного поиска или с авторизованным доступом.

1. Регистрация `vedelo.ru` выполнена; отдельно проверить обозначение «Ведело» в классах МКТУ 9, 35 и 42 и сохранить результат проверки.
2. Настроить DNS и TLS для `vedelo.ru`, `www.vedelo.ru`, `artistcrm.ru` и `www.artistcrm.ru` на один deployment.
3. Установить `DOMAIN=https://vedelo.ru` и `NEXTAUTH_URL=https://vedelo.ru`.
4. Добавить разрешённые callback URL обоих доменов в Google OAuth, VK ID и платёжных кабинетах. Приложение выбирает callback по доверенному host запроса; cookies между доменами не переносятся.
5. Проверить, что manifest и `/service-worker.js` доступны с обоих origin без редиректа.
6. Сохранить старый домен во владении после кампании.

## Запуск 30-дневной кампании

Задать один и тот же ISO-8601 момент во всех экземплярах приложения:

```env
BRAND_MIGRATION_STARTED_AT=2026-10-01T00:00:00+07:00
```

- Дни 1–14: закрываемая плашка с безопасным переносом входа.
- Дни 15–29: постоянная плашка и счётчик оставшихся дней.
- С 30-го дня: кабинет на старом origin заменяется migration-shell.

Дата не должна меняться после запуска. Пустое или некорректное значение отключает кампанию. Для отмены до 30-го дня значение можно убрать и повторно развернуть приложение; уже использованные одноразовые коды остаются погашенными.

## Перенос сессии

Старая PWA запрашивает одноразовый непрозрачный код через `POST /api/domain-migration/issue`. В базе хранится только SHA-256 hash; код действует пять минут, связан с пользователем, tenant и целевым origin и погашается атомарно. Он передаётся новому origin во fragment URL, поэтому не попадает в HTTP referrer или серверные access-логи. Страница `/migrate` сразу очищает URL и создаёт обычную NextAuth-сессию через provider `domain-migration`.

Если сессия старого origin истекла, пользователь входит на `vedelo.ru` обычным способом. Старую установленную иконку пользователь удаляет вручную.

## Push

Новые web push-подписки получают серверное поле `webAppOrigin`. Записи без этого поля считаются подписками ArtistCRM. После успешной подписки на `vedelo.ru` отключается только старая подписка того же migration-сеанса и устройства.

Начиная с 30-го дня обычные уведомления отправляются только подпискам `vedelo`. Один раз вызвать защищённый endpoint:

```text
POST /api/push/domain-migration
Authorization: Bearer <PUSH_REMINDERS_CRON_SECRET или CRON_SECRET>
```

Его можно безопасно вызывать повторно по расписанию: он пакетами отправляет последнее уведомление ещё не обработанным старым подпискам и затем отключает их. Завершение подтверждается ответом с `processed: 0`.

## Redirect matrix

- Публичные HTML-страницы старого домена: `301` на тот же путь `vedelo.ru`.
- Внешние API и webhooks: `308` с сохранением метода и тела.
- `/manifest.json`, service worker, иконки, `/migrate` и endpoints переноса не перенаправляются.
- В дни 1–29 старый кабинет и его API продолжают обслуживаться. С 30-го дня навигация кабинета получает migration-shell, деловые и auth API отвечают `410`, а на старом origin остаётся только `/api/push/unsubscribe` для отключения прежней подписки.

## Проверка релиза

- Chrome/Edge desktop и Android: обновление старой PWA, перенос, установка новой PWA, ручное удаление старого ярлыка.
- Safari/iOS: запуск со старого ярлыка, перенос авторизации и ручная установка через «На экран Домой».
- Проверить дни 1, 14, 15, 29 и 30 на staging с отдельной базой и фиксированным временем.
- Проверить одноразовость, истечение пяти минут, tenant isolation и отсутствие кода в URL после загрузки.
- Проверить offline-запуск до первого подключения и первый online-запуск после блокировки.
- Проверить Google OAuth, VK ID, YooKassa, Точка, webhooks, `301/308`, canonical, sitemap и отсутствие redirect loop.
- Проверить отсутствие дублей push и отключение только соответствующей старой подписки.

## Терминология

`SiteSettings.custom.primaryEntityTerminology` принимает `auto`, `events`, `orders`. В `auto` специализация `events` и неизвестная/пустая специализация используют «мероприятия», остальные известные специализации — «заказы». Ручной выбор имеет приоритет. Внутренние контракты при этом остаются прежними.
