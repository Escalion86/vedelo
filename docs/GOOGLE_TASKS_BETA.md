# Google Tasks: эксперимент для разработчика

## Подключение новых разрешений

1. Откройте [Google Cloud Console](https://console.cloud.google.com/) и выберите
   **тот же проект**, в котором создан используемый Ведело OAuth client.
2. В **APIs & Services → Library** найдите **Google Tasks API** и нажмите **Enable**.
   Google Calendar API оставьте включённым.
3. Откройте **Google Auth Platform → Data Access → Add or remove scopes**.
   Добавьте `https://www.googleapis.com/auth/tasks` и сохраните изменения.
   Существующий scope Calendar не удаляйте. Доступ Tasks разрешает управление всеми
   задачами аккаунта; отдельного scope только для списка «Ведело» у Google нет.
4. Если OAuth-приложение уже опубликовано, не переводите его в Testing ради этой
   функции: это затронет остальных пользователей. Проверьте требования Google
   к подтверждению добавленного scope в **Verification Center**. Если приложение
   уже в Testing, добавьте свой Google-аккаунт в **Audience → Test users**.
5. В **Clients** используйте прежний OAuth client и прежний callback:
   `https://vedelo.ru/api/google-calendar/callback`. Для локального стенда нужен
   отдельный разрешённый URI с точным локальным origin, например
   `http://localhost:3000/api/google-calendar/callback`.
   Новые client ID/secret и новые переменные окружения не требуются.
6. После установки обновления войдите в Ведело **с ролью dev**, без входа от имени
   другого пользователя. Откройте **Настройки → Интеграции → Google Calendar**.
   Сначала подключите обычный календарь, если он ещё не подключён.
7. В блоке **Google Tasks · тест для разработчика** нажмите **Разрешить Google Tasks**.
   Выберите **тот же Google-аккаунт**, что уже используется для календаря, и разрешите
   Tasks и Calendar. Кнопка запрашивает повторное согласие и offline-доступ;
   OAuth-токены сохраняются на сервере автоматически. Не копируйте их вручную.
8. В Google Tasks при необходимости создайте список «Ведело». В настройках Ведело
   выберите этот список, способ по умолчанию и нажмите **Включить тестовую функцию**.

Если Google Tasks API выключен, настройки покажут ошибку чтения Tasks. Включите
API в правильном проекте и обновите страницу. Если доступ Tasks не был разрешён,
кнопка запроса разрешений останется доступна. При `invalid_grant` повторно пройдите
авторизацию. `redirect_uri_mismatch` означает несовпадение callback и разрешённого URI.

Источники: [настройка Google Tasks API](https://developers.google.com/workspace/tasks/quickstart/js),
[scopes Tasks](https://developers.google.com/workspace/tasks/auth),
[OAuth web server flow](https://developers.google.com/identity/protocols/oauth2/web-server),
[контракт даты и выполнения](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks).

## Поведение

- Функция opt-in: только `role=dev`, без impersonation, при действующем тарифном
  доступе Calendar. Остальным пользователям не показывается и запрещена сервером.
- В общем редакторе дополнительных задач: **Событие / Задача / Не синхронизировать**.
  Поле видно после включения эксперимента при подключённом Google. При паузе
  остаётся видимым с пояснением. Для события длительность 5–1440 минут, default 30.
- Значение по умолчанию подставляется в новые задачи обычного редактора и POST/PUT
  событий. Существующие записи сохраняют режим «Событие». Внутренние автоматические
  создатели задач (например, КП/телефония) пока сохраняют прежний режим «Событие».
- Дата Google Tasks — календарный день в часовом поясе организации. API не позволяет
  читать или задавать точное время. Время в CRM и её собственные push не удаляются.
- Выполнение события удаляет его из Calendar; возврат создаёт новое. У Google Tasks
  меняется `completed / needsAction`. Задачи без даты остаются в Tasks; события без
  даты не отправляются. Удаление задачи/заказа удаляет связанные внешние записи.
- Описание Tasks содержит «Задача по мероприятию/заказу», текст задачи и сведения
  связанной работы: название по выбранному режиму, дату и место. Описание работы,
  клиент/контакты, коллега, прочие контакты, финансы/транзакции, список задач,
  навигация и ссылка включаются по общим настройкам синхронизации заказов.
  Изменения применяются к существующим задачам при очередной синхронизации.
  Длинный текст обрезается до лимита notes с сохранением ссылки и recovery marker.
- Галочка и её снятие в Google Tasks возвращаются в CRM. Заголовок, описание и дата
  редактируются в CRM. При одновременной смене выполнения с обеих сторон CRM имеет
  приоритет. Обновление отметки защищено сравнением текущей задачи в Mongo и меняет
  `syncVersion`; при конфликте повторяется позднее.
- Обратная проверка запускается раз в минуту **при открытом видимом кабинете dev**
  и доступной сети, либо вручную кнопкой **Синхронизировать задачи**. Постоянного cron
  нет. Фоновая партия — 20 наиболее давно проверенных связей, поэтому у большого
  числа записей обход занимает несколько минут. Сохранение заказа проверяет до 100
  его связей. Остаток обходит фоновая проверка.
- Изменение значения по умолчанию не преобразует старые записи. Смена списка Tasks
  задаёт место новых задач; существующие продолжают использовать сохранённый список.
- Задачи не исключаются из синхронизации из-за отмены или передачи основного заказа.
  Непроверенный импорт из файла/Google не отправляется. Общая пауза и отключение
  интеграции прекращают обращения к Google; внешние копии автоматически не удаляются.
- Удаление в Google не удаляет задачу CRM. В настройках появляется сообщение и
  действие **Восстановить в Google**. Переключение режима также задаёт новое размещение.

## Надёжность и границы теста

Стабильный `_id` подзадачи сохраняется при обычном обновлении. Provider IDs берутся
из доверенного серверного снимка; новый клиентский ID не становится внешней связью.
`GoogleAdditionalLinks` хранит tenant/user/event/task, вид и место внешней записи,
маркер создания, последний флаг выполнения, ошибку и lease. Клиент не управляет
этими полями. Все запросы новой коллекции ограничены tenant и пользователем.

При смене вида сначала удаляется прежняя копия с фиксацией прогресса, затем создаётся
новая. Это возобновляемая последовательность, а не распределённая транзакция.
Calendar использует задаваемый сервером ID; для Tasks маркер в notes позволяет
найти запись при потере ответа создания. Не удаляйте строку `[vedelo:…]` из notes.
Если результат создания не удалось подтвердить, повтор ищет запись (до 500 Tasks),
но не вставляет новую вслепую. Состояния unknown/ambiguous требуют ручной сверки
разработчиком. Нельзя просто очищать pendingCreate в БД без проверки Google.

Смена Google-аккаунта для уже связанных задач не входит в эксперимент: для расширения
разрешений выбирайте прежний аккаунт. Для нативного Android новые элементы интерфейса
не добавлялись; существующие поля режима сохраняются сервером при обновлении по ID.
После включения эксперимента для остановки используйте общую паузу Google Calendar;
автоматическое возвращение на прежний механизм синхронизации не выполняется.

## Проверка

`node --test tests/server/googleTasksBeta.test.cjs` запускает отдельную временную MongoDB
и mock Google. Для другого расположения mongod задайте `GOOGLE_TASKS_TEST_MONGOD`.
Проверяются CRUD, интервалы, timezone, двустороннее выполнение, удаление/восстановление,
потеря ответа, повторы, параллельные запросы, dev/impersonation/tariff и tenant-negative.
Реальные OAuth и Google Tasks требуют ручной приёмки после настройки Cloud Console.

Локальная приёмка 25.10.2026: 21 server/helper проверка без пропусков, точечный ESLint
и итоговая Next.js production-сборка `--webpack` (`.next-google-tasks-qa`) прошли.
Сборка использовала временную MongoDB, рабочие `.env` не загружались.
Playwright/Edge-стенд настоящих GoogleCalendarSettings, редактора и ModalsPortal с
mock API проверил 390/1365 px × light/dark, сохранение event/task/none и длительности,
скрытие у user и без подключения, пояснение паузы и отсутствие ошибок console/page.
Исходник стенда и снимки сохранены вне репозитория в системной временной папке.
Production, реальные аккаунты Google, телефоны и внешние записи не менялись.
