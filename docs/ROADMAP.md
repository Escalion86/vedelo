# Product Roadmap And Checklist

---

## Цели продукта (текущий фокус)

- Не терять заявки и не забывать перезвоны.
- Не терять контроль по задаткам и оплатам.
- Не пропускать мероприятия.
- Упростить подготовку документов (договор/счет/акт).
- Дать базовую интеграцию входящих заявок с сайта (API/Tilda).
- Подготовить полноценное мобильное приложение (React Native + Expo) для надежных уведомлений и мобильных сценариев.
- Реализовать offline-first: создание/редактирование данных без интернета с последующей синхронизацией на сервер.

---

## Смежные продуктовые треки

- Второй продукт для компаний event-сегмента: `docs/PARTYCRM_ROADMAP.md`.
- Быстрое восстановление контекста PartyCRM: `docs/PARTYCRM_CONTEXT.md`.
- Рабочее название: PartyCRM.
- Стратегия: отдельный бренд/домен/позиционирование, но переиспользование технологического ядра ArtistCRM на раннем этапе.
- Текущее архитектурное решение PartyCRM: один User может работать с несколькими компаниями, исполнитель может быть связан с несколькими компаниями, а подрядчик может существовать как карточка без аккаунта до ручной привязки.

---

## KPI запуска (контроль результата)

- Доля заявок с хотя бы одним запланированным `additionalEvents` > 90%.
- Доля просроченных доп. событий (без переноса/закрытия) < 15%.
- Доля мероприятий с задатком до даты события > 80%.
- Доля пропущенных мероприятий ~= 0%.
- Конверсия `заявка -> подтверждено` и `подтверждено -> проведено` растет.

## Технические требования (единые)

- Единый формат ошибок API: `{ success:false, error:{ code, type, message } }`.
- Mobile first для всех критичных сценариев.
- Безопасные логи (без персональных данных в открытом виде).
- Соответствие требованиям РФ по обработке персональных данных.
- Для критичных действий (создание/изменение заявки): отсутствие сети не должно приводить к потере данных.

## Следующие шаги (ближайшие)

Порядок согласован пользователем 09.09.2026 и имеет приоритет над общими группами P0–P3. Остальные треки сохраняются в roadmap; этот порядок не означает их отмену.

1. Актуализировать статусы планов по коду и подтверждённым проверкам. Основные противоречия roadmap исправлены 09.09.2026: OPT-T9, «Важное», offline, security и Mobile Track. Пустые чекбоксы старых пошаговых планов не считать самостоятельным backlog; наличие кода не заменяет production/device QA.
2. Закрыть критические сквозные проверки и восстановление из резервной копии. Пройти `docs/ARTISTCRM_RELEASE_SMOKE_RUNBOOK.md`: авторизация, заявка → мероприятие → задаток/оплаты → документы → закрытие, PWA/push/offline, внешние интеграции и разделение данных пользователей. По `docs/ARTISTCRM_BACKUP_RESTORE_RUNBOOK.md` подтвердить наличие копии и успешное восстановление в отдельную тестовую базу. Записать среду, дату, результат и оставшиеся блокеры; автотесты и локальная сборка сами по себе этот этап не закрывают.
3. Добавить «Заявки без следующего шага» в «Важное»: открытые заявки без запланированной невыполненной задачи в `additionalEvents`, переход в заявку и быстрое назначение следующего контакта. Не вводить второй независимый источник задач; уточнить граничные случаи до реализации и проверить обновление списка после назначения контакта.
