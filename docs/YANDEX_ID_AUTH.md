# Яндекс ID и управление способами входа

## Что реализовано

Web/PWA поддерживает вход через Яндекс ID. Раздел
«Настройки сайта → Авторизация» (`/cabinet/phone-auth`) содержит независимые
переключатели VK ID и Яндекс ID. Доступ к этому разделу, как и прежде,
имеет разработчик (`role=dev`), вне режима входа за другого пользователя.

Настройки глобальные, применяются ко всему сервису. Секреты не вводятся
в интерфейсе и не хранятся в SiteSettings. Признак «ключи настроены» означает
наличие переменных окружения, а не успешную проверку Яндексом.

Яндекс по умолчанию выключен. VK до первого сохранения наследует прежний
`VK_AUTH_ENABLED`; после сохранения решение принимает настройка в базе.
Перезапуск сервера для изменения переключателей не нужен. Открытую страницу
входа следует обновить, чтобы кнопки отразили настройку. API проверяет её
при каждом новом входе. Уже выданные сессии не отзываются.

## 1. Зарегистрировать приложение в Яндексе

1. Войти в аккаунт владельца, доступ к которому будет сохраняться.
2. Открыть https://oauth.yandex.ru/client/new/id/ и создать приложение
   **для авторизации пользователей**.
3. Название — **Ведело**. Прикрепить существующую иконку продукта и указать
   рабочую контактную почту.
4. Платформа — **Веб-сервисы**.
5. Redirect URI указать точно:

   ```text
   https://vedelo.ru/api/yandex-id/callback
   ```

6. В доступе к данным обязательны «Логин, имя и фамилия, пол»
   (`login:info`) и «Номер телефона» (`login:default_phone`).
   Уже добавленные права на почту и портрет можно оставить. Код запрашивает
   только два обязательных разрешения; почта, портрет, имя и пол не импортируются.
   Телефон из `default_phone.number` определяет аккаунт CRM. Для существующего
   аккаунта успешный OAuth Яндекса достаточен для входа, без пароля CRM.
7. Сохранить приложение. На странице приложения найти **Client ID** и
   **Client secret**.
8. Пройти предложенную Яндексом верификацию сервиса. По документации Яндекса
   без неё пользователю может показываться предупреждение перед выдачей доступа.

Используется обмен кодом OAuth с PKCE, а не виджет мгновенной авторизации.
Вспомогательную HTML-страницу приёма токена и скрипт виджета добавлять не надо.

Официальные инструкции:

- [Создание приложения](https://yandex.ru/dev/id/doc/ru/register-auth).
- [Обмен кодом и PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url).
- [Поля профиля](https://yandex.ru/dev/id/doc/ru/user-information).

## 2. Настроить окружение сервера

Добавить в фактическое окружение процесса Next.js:

```dotenv
YANDEX_ID_CLIENT_ID=идентификатор_вашего_приложения
YANDEX_ID_CLIENT_SECRET=секрет_вашего_приложения
YANDEX_ID_REDIRECT_URI=https://vedelo.ru/api/yandex-id/callback
```

`NEXTAUTH_URL` и `DOMAIN` должны соответствовать `https://vedelo.ru`;
существующий `NEXTAUTH_SECRET` менять не нужно.
Не использовать `NEXT_PUBLIC_` для секрета. Не коммитить реальные значения.
Шаблоны переменных — `.env.example` и `.env.deploy.example`.

Выложить код и перезапустить процесс Next.js с обновлённым окружением
обычным способом деплоя проекта. Если используется менеджер процессов,
убедиться, что он действительно перечитал переменные.

Нужен исходящий HTTPS-доступ сервера к `oauth.yandex.ru` и `login.yandex.ru`.
В настройках reverse proxy/access logs исключить query string callback
`/api/yandex-id/callback`: там на короткое время присутствует OAuth-код.
Приложение не выводит этот код и ответы провайдера в свои логи.

Модель создаёт коллекцию временных операций `yandexauthflows` с TTL-индексом
и уникальный sparse-индекс `Users.yandexId`. У пользователя БД должны быть
права на создание индексов. При привязке сервер дожидается инициализации
индексов; не отключать их создание без предварительной ручной подготовки.
Переписывать старые записи Users или мигрировать бизнес-данные не нужно.

## 3. Включить в «Ведело»

1. Войти обычным способом под разработчиком.
2. Открыть **Настройки сайта → Авторизация**.
3. В блоке **Вход через внешние сервисы** проверить статус ключей Яндекса.
4. Нажать переключатель **Яндекс ID: отключён**, чтобы стало **включён**.
5. Нажать **Сохранить**.
6. Открыть `/login` в отдельном приватном окне: должна появиться кнопка
   **Войти с Яндекс ID**.

Если переключатель недоступен, проверить все три переменные и перезапуск.
Наличие ключей VK не зависит от Яндекса, переключатели независимы.

## 4. Управление VK ID

Для VK сохраняются существующие переменные:

```dotenv
VK_ID_APP_ID=идентификатор_приложения_VK
VK_ID_CLIENT_SECRET=секрет_приложения_VK
VK_ID_REDIRECT_URI=https://vedelo.ru/api/vk-id/callback
```

Если VK уже работал, менять приложение или ключи не нужно.
В том же разделе включить или выключить **VK ID**, затем сохранить.
`VK_AUTH_ENABLED` нужен только как совместимый начальный fallback:
явное сохранённое значение имеет приоритет, в том числе над `false` в env.

Отключение закрывает Web/PWA API и мобильный endpoint VK.
У ранее установленного Android кнопка VK может остаться видимой, но сервер
вернёт сообщение, что способ отключён. Нативный вход через Яндекс
в эту Web/PWA-реализацию не входит; APK и package ID не менялись.

## 5. Как проходит первый вход

1. Пользователь нажимает **Войти с Яндекс ID**, входит в Яндекс
   и разрешает доступ.
2. Сервер получает телефон Яндекса, нормализует его к `7XXXXXXXXXX` и ищет
   аккаунт по номеру. Без подходящего телефона продолжение запрещено.
   Далее:
   - для существующего номера — автоматически подключает Яндекс ID, если
     привязки ещё нет, и открывает соответствующий кабинет. Повторный ввод
     пароля и кнопки подтверждения не нужны;
   - для нового — **Зарегистрироваться через Яндекс**. Форма получает номер
     из серверной pending-операции, без передачи номера через URL.
     Телефон регистрации зафиксирован; остаются подтверждение телефона,
     пароль и юридические согласия. Это регистрация через Яндекс с
     дополнительной проверкой телефона, а не автоматическое создание аккаунта.
3. После регистрации пользователь возвращается на страницу завершения
   авторизации и автоматически попадает в кабинет.
4. Уже открытая сессия не определяет целевой аккаунт: сервер выбирает его
   исключительно по номеру из OAuth-профиля Яндекса. Для регистрации нового
   номера из другой сессии предусмотрен выход с возвратом к регистрации.
5. Следующие входы: авторизация Яндекса → автоматический переход в кабинет. Номер
   проверяется заново при каждом входе и при погашении одноразового билета.

Ожидающая привязка действует 15 минут и привязана к cookie того же браузера.
Если время вышло или браузер сменился, начать вход через Яндекс снова.
Старое действие явной привязки `link` сохраняет проверку текущей сессии/tenant
и запрет impersonation для совместимости. Новый UI использует `login`;
успешный вход создаёт обычную сессию без impersonation.
Один аккаунт может иметь один Яндекс ID; один Яндекс ID — только один
аккаунт. Конфликт не перезаписывает существующую привязку.
Автоматического объединения аккаунтов по телефону или email нет.
Смена телефона в Яндексе не меняет телефон CRM и блокирует вход через
несовпадающую привязку. Даже если новый номер принадлежит другому аккаунту,
привязка автоматически не переносится. Восстановите совпадение номеров
или войдите обычным способом. Старые pending/ticket без телефона недействительны.
Отвязка/замена Яндекс ID через интерфейс пока не предусмотрена.

## 6. Проверить после выкладки

1. Без сессии CRM войти через Яндекс с номером существующего тестового
   аккаунта без привязки: кабинет должен открыться автоматически, без пароля.
2. Убедиться, что открылся прежний кабинет с прежними заказами и клиентами.
3. Выйти и повторить вход через Яндекс: повторная проверка телефона не нужна.
4. Для нового тестового пользователя пройти регистрацию с согласиями,
   подтверждением телефона и автоматическим входом после возврата.
5. Проверить отказ от согласия в Яндексе и повторную попытку.
6. Выключить Яндекс, сохранить и обновить `/login`: кнопки нет.
   Попытка начать вход прямой ссылкой также запрещена.
7. Проверить независимое отключение/включение VK. Обычный вход по паролю
   продолжает работать.
8. Повторить вход в установленной PWA на телефоне: внешний браузер
   и PWA должны сохранять cookie в используемом сценарии. Если системный
   браузер открыл отдельную сессию, завершить вход в том же браузере.

Эти действия с реальными приложениями провайдеров выполняются после
настройки ключей и выкладки; локальные mocks не подтверждают их прохождение.

Дополнительно: проверить отказ при отсутствии телефона Яндекса,
первую регистрацию нового номера и выбор аккаунта по телефону Яндекса,
даже если открыта другая сессия CRM. После смены номера в Яндексе вход
через прежнюю привязку должен блокироваться, без переноса кабинета.

## Локальные проверки

```powershell
$env:YANDEX_TEST_MONGOD='C:/Program Files/MongoDB/Server/6.0/bin/mongod.exe'
node --test tests/server/yandexAuth.test.cjs
node --test tests/components/socialAuth.browser.test.cjs
# После сборки в изолированный NEXT_DIST_DIR:
$env:NEXT_DIST_DIR='.next-yandex-auth'
node --test tests/server/yandexAuth.http.test.cjs
```

Первый тест запускает отдельную временную MongoDB, не читает production env
и проверяет реальные индексы и атомарное погашение операций. OAuth-запросы
заменены mock-ответами. Проверяются state/PKCE, повтор callback, другая
OAuth application, TTL, конфликт привязок, tenant-negative сценарии,
отключение VK/Яндекса и доступ к административным настройкам.

Браузерный тест использует реальные компоненты/CSS и mock API, Playwright
с Edge, 390/1365 px × светлая/тёмная темы. Проверяются сохранение и перечитывание
настроек, клавиатура, видимость кнопки Яндекса, явная привязка/вход и ошибки.
Снимки сохраняются вне репозитория: `%TEMP%/vedelo-social-auth-qa`
или каталог из `QA_SCREENSHOT_DIR`.

HTTP-тест запускает собранное приложение с отдельной MongoDB и тестовым
окружением. Проверяет настоящие cookie/CSRF/NextAuth endpoints: обычный вход,
явную привязку, новую сессию Яндекса с прежним tenant и административное
отключение провайдера. Успешный ответ Яндекса здесь заменяется подготовленной
pending-операцией; реальные OAuth endpoints этим тестом не вызываются.

Локальная приёмка 1.39.0 от 20.10.2026: 26 серверных проверок (Яндекс + телефон/SMS),
HTTP-сценарий на production-сборке и браузерная матрица прошли без пропусков.
Точечный ESLint без ошибок и предупреждений; `next build --webpack` успешен
при `NODE_OPTIONS=--max-old-space-size=6144`. Первая попытка с лимитом около
1 ГБ завершилась исчерпанием памяти. Сборка использовала временную локальную
БД; реальные аккаунты Яндекса/VK, production и установленная PWA не проверялись.

Для ручного локального OAuth использовать отдельное приложение Яндекса
с Redirect URI `http://localhost:3000/api/yandex-id/callback`,
те же три переменные с тестовыми значениями и только локальную тестовую БД.

Приёмка 1.39.1: 28 серверных проверок (Яндекс + телефон/SMS), браузерная
матрица 390/1365 × светлая/тёмная тема, HTTP-проверка настоящей NextAuth-сессии
с отказом при несовпадающем номере прошли. ESLint и Webpack-сборка успешны.
OAuth-профиль в автоматических тестах заменён mock; боевой Яндекс и Android
не проверялись и не выкладывались.

Приёмка 1.39.2 (21.10.2026): 29 серверных проверок, ESLint и Webpack-сборка
прошли. Браузерный стенд 390/1365 × две темы проверяет кнопку, регистрацию,
автоматический первый/повторный вход, отсутствие повторных POST в StrictMode
и ошибку NextAuth. HTTP-тест готовой сборки дополнительно открывает настоящую
страницу завершения в Edge без сессии CRM и без сохранённой привязки:
автоматический переход в кабинет и правильные user/tenant подтверждены.
В этом тесте результат OAuth подставляется в изолированную MongoDB;
боевой Яндекс и production не изменялись.
