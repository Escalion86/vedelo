# Стандарты интерфейса Web/PWA

Этот документ — источник правды для новых и изменяемых экранов кабинета. Он
описывает повторяемые элементы, а не внешний вид конкретного раздела. Старые
экраны приводятся к стандарту только в рамках отдельной задачи: не нужно
перекрашивать соседний интерфейс попутно.

## Основные принципы

- Смысл действия определяет компонент и вариант оформления. Не назначать цвет
  по вкусу конкретного экрана.
- Цвет не должен быть единственным носителем смысла: сохранять текст, иконку,
  `title`/`aria-label` и понятное состояние.
- Использовать готовые компоненты и CSS-переменные темы. Не копировать их набор
  классов и не добавлять локальные hex/RGB для стандартного состояния.
- На одном экране должно быть одно очевидное основное действие. Остальные
  действия визуально слабее.
- Проверять светлую и тёмную тему, ширину 390 px, клавиатурный фокус,
  `disabled`/`loading` и фактический результат действия.

## Текстовые кнопки

Для текстовых действий использовать `components/AppButton.js`.

| Смысл                                        | `variant`   | Примеры                                        |
| -------------------------------------------- | ----------- | ---------------------------------------------- |
| Главное действие экрана или формы            | `primary`   | «Сохранить», «Создать», «Опубликовать»         |
| Вспомогательное действие                     | `secondary` | «Выбрать», «Предпросмотр», «Отмена», «Закрыть» |
| Малозаметное действие без отдельного акцента | `ghost`     | раскрытие дополнительных возможностей          |
| Необратимое или разрушительное действие      | `danger`    | «Удалить», «Отозвать доступ»                   |

- `md` — обычное действие, `sm` — локальное действие в карточке или компактной
  панели, `lg` — только для редкого главного CTA на свободном экране.
- Не использовать `danger` для обычной отмены или закрытия. Кнопка «Отмена» —
  `secondary`.
- Во время запроса блокировать повторное нажатие, сохранять подпись действия или
  показывать понятное состояние загрузки и ставить `aria-busy`.
- Группа кнопок должна переноситься на узком экране. Не уменьшать touch-target
  ниже 40 px ради размещения в одну строку.
- Футер модального окна строить через `layouts/modals/ModalButtons.js`, если его
  контракт покрывает сценарий.

## Редактирование и удаление полей, строк и карточек

Для действий только с иконкой использовать `IconActionButton` /
`ActionIconButton`; для добавления — `AddIconButton`.

| Действие             | Иконка                         | `variant` | Доступная подпись |
| -------------------- | ------------------------------ | --------- | ----------------- |
| Редактировать        | `faPencilAlt`                  | `warning` | «Редактировать …» |
| Удалить              | `faTrashAlt`                   | `danger`  | «Удалить …»       |
| Добавить             | `faPlus` через `AddIconButton` | `success` | «Добавить …»      |
| Нейтральное действие | подходящая однозначная иконка  | `neutral` | глагол + объект   |

Очистка выбранной связи в полях клиента/мероприятия: `faEraser`, `danger`,
подпись «Очистить выбор …». Это согласованный вариант сброса связи, а не удаления
сущности. Кнопка находится внутри `InputWrapper`, рядом с другими действиями поля.

- В горизонтальной группе порядок: редактирование, затем удаление. Кнопки одной
  группы имеют одинаковый `size`; по умолчанию `base`, в тесной строке `sm`.
- Всегда передавать осмысленный `title`: базовый компонент использует его и как
  `aria-label`. Не использовать подписи «Изменить» или «Удалить» без объекта,
  если на экране несколько сущностей.
- Карандаш означает изменение данных, корзина — удаление данных, крестик —
  только закрытие или сброс. Не заменять корзину крестиком в овальном
  `AppButton`.
- Цвет редактирования — предупреждающий оранжевый, удаления — красный,
  добавления — зелёный. Цвета берутся из вариантов компонента и уже имеют
  отдельные значения для тёмной темы.
- Удаление сохранённой сущности требует подтверждения с названием или понятным
  описанием объекта и кнопкой `danger`. Удаление новой несохранённой строки
  можно выполнять сразу, если данные легко восстановить повторным добавлением.
- После подтверждённого сервером удаления показать один итоговый Toast. При
  ошибке объект остаётся в интерфейсе, а пользователь получает ошибку без
  технических деталей и секретов.
- Свайп карточки следует тем же значениям: редактирование — `warning`, удаление
  — `danger`; наличие свайпа не отменяет доступные кнопки или меню для
  клавиатуры и desktop.

## Семантические цвета

Цвета применяются через варианты компонентов и переменные из `app/globals.css`.

| Семантика             | Где применять                                         | Где не применять                     |
| --------------------- | ----------------------------------------------------- | ------------------------------------ |
| `primary` / песочный  | главное действие, выбранное состояние, фокус          | декоративная заливка всех кнопок     |
| `success` / зелёный   | успешный результат, добавление, подтверждённый статус | обычное сохранение до ответа сервера |
| `warning` / оранжевый | редактирование, риск, требующий внимания              | обычная справка                      |
| `danger` / красный    | удаление, критическая ошибка, необратимое действие    | отмена и закрытие                    |
| `info` / синий        | нейтральная справка о процессе или возможности        | успешный результат                   |
| `neutral`             | вторичные сведения и действия                         | ошибки и разрушительные действия     |

Не кодировать бизнес-статус только цветом: рядом нужны текст и, когда уместно,
иконка. Нестандартное цветное состояние должно иметь явную проверку тёмной темы
и обоснование, почему стандартные варианты не подходят.

## Toast-уведомления

Единая точка вызова — `helpers/useSnackbar.js`:

```js
const snackbar = useSnackbar()

snackbar.success('Изменения сохранены')
snackbar.warning('Проверьте дату следующего контакта')
snackbar.error('Не удалось сохранить изменения')
snackbar.info('Ссылка скопирована')
```

### Когда показывать

- `success` — короткое подтверждение завершённого действия: сохранено, удалено,
  отправлено, подключено. Только после фактического успеха сервера.
- `error` — действие не выполнено и пользователь может повторить его или
  исправить ввод. Не показывать сырой stack trace, payload, токен или текст
  внутренней ошибки сервера.
- `warning` — действие выполнено частично либо нужно внимание пользователя,
  но текущий экран остаётся рабочим.
- `info` — краткий результат без оценки, например копирование. `default` не
  использовать в новом коде: смысл уведомления должен быть определён.

### Правила поведения и текста

- Одно пользовательское действие — один итоговый Toast. Не показывать отдельные
  уведомления для промежуточного сохранения и последующей публикации.
- Не показывать Toast при начале загрузки. Загрузка отражается на самой кнопке
  или контроле.
- Сообщение — одно короткое предложение без точки в конце, обычно в форме
  результата: «Клиент сохранён», «Не удалось удалить документ».
- Не дублировать одновременно один и тот же результат через Toast, `Notice` и
  текст у кнопки.
- Стандартное время скрытия задаёт `AppSnackbarProvider`; менять его локально
  допустимо только когда пользователю объективно нужно больше времени прочитать
  сообщение. Критическая ошибка, которую нельзя потерять, должна быть `Notice`,
  а не бесконечным Toast.
- Повторы одинакового уведомления подавляет общий provider. Не обходить его
  прямым `enqueueSnackbar`.
- Toast не содержит единственный путь продолжения важного сценария: действие
  должно оставаться доступным на экране.

## Toast или постоянный Notice

`components/Notice.js` остаётся в контексте экрана, пока причина актуальна.

| Ситуация                                                          | Компонент                 |
| ----------------------------------------------------------------- | ------------------------- |
| «Сохранено», «Удалено», «Скопировано»                             | Toast                     |
| Ошибка разового действия с возможностью повторить                 | Toast `error`             |
| Ошибка загрузки раздела или поля, из-за которой работа невозможна | `Notice tone="error"`     |
| Важное ограничение тарифа, настройки или данных                   | `Notice` подходящего tone |
| Пояснение поля или раздела                                        | `FieldHelp` рядом с заголовком |

Для `Notice` использовать `role="alert"` у актуальной критической ошибки и
`role="status"` у появившегося некритичного результата. Не создавать локальные
зелёные/красные плашки вместо `Notice`.

## Поля и формы

- Базовые поля: существующие `Input`, `Textarea`, `ComboBox` и `InputWrapper` с
  явной подписью.
- Высоту полей не задавать локальными `h-*`/`min-h-*` поверх `InputWrapper`.
- Текст — `Input`, выбор — `ComboBox`, описание — `Textarea`.
- Денежные суммы — `Input type="number" min={0}` со стандартными стрелками и
  `postfix="₽"`; для копеек — `decimalScale={2}`.
- Ошибку валидации, относящуюся к одному полю, показывать у поля, а не только
  Toast. Итоговую серверную ошибку формы можно дополнить Toast или `Notice` в
  зависимости от того, исчезает ли она после следующего действия.

## Модальные окна и структура экрана

- Использовать стандартный стек `modalsFunc.add` и повторно использовать готовые
  окна выбора, включая `selectEventServicesFunc`.
- Не дублировать заголовок раздела внутри его содержимого. Количество элементов
  и короткую сводку показывать в подписи раздела.
- Закрытие окна с несохранёнными изменениями требует подтверждения; обычное
  закрытие — нет.
- Предпросмотр клиентской страницы сохраняет оформление самой публичной
  страницы, а не тему кабинета.

## Чек-лист изменения UI

- Использованы общие компоненты, семантические варианты и токены темы.
- Есть понятные `title`/`aria-label`, focus-visible и клавиатурный путь.
- Основное, вторичное и разрушительное действия различимы без опоры только на
  цвет.
- Удаление сохранённых данных подтверждается; повторный запрос заблокирован.
- Результат действия сообщает ровно один Toast либо контекстный `Notice`.
- Проверены desktop, 390 px, светлая и тёмная темы, loading, disabled и ошибка.

В карточках списков стандартные кнопки редактирования/удаления размещать справа от названия и подписи: слева `min-w-0 flex-1` с переносом длинного текста, справа группа `shrink-0`. Не выносить эти кнопки отдельной строкой под карточкой.

## Подсказки полей и разделов

Использовать `help` у `Input`, `Textarea`, `ComboBox`, `InputWrapper` и `LabeledContainer`; для самостоятельного заголовка — `FieldHelp text={...} label="Название поля"`. Значок «i» находится справа от подписи. Подсказка открывается нажатием (также Enter/Space), закрывается повторным нажатием, снаружи, при уходе фокуса или Escape. Не прятать в подсказке ошибки, актуальные ограничения и обязательные действия. Текст объясняет назначение поля и последствия выбора; не дублирует название.
