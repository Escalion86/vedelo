# Maestro-сценарии Android

Production-сценарии рассчитаны на установленный build с package ID `ru.escalion.vedelo`; development build использует `ru.escalion.vedelo.dev`. Основные deep-link сценарии открываются через `vedelo://`, legacy `artistcrm://` проверяется отдельно при регрессионной QA. Перед offline- и deep-link сценариями пользователь должен быть авторизован; `login.yaml` очищает состояние приложения и создаёт эту сессию.

Запуск основного smoke-набора на подключённом Android-устройстве:

```bash
maestro test -e TEST_PHONE=+79990000000 -e TEST_PASSWORD=secret mobile/maestro/login.yaml
maestro test -e TEST_ONBOARDING_PHONE=+79990000001 -e TEST_ONBOARDING_PASSWORD=secret mobile/maestro/onboarding.yaml
maestro test mobile/maestro/deep-links.yaml
maestro test mobile/maestro/offline-client.yaml
maestro test mobile/maestro/offline-event.yaml
maestro test mobile/maestro/event-calendar.yaml
maestro test mobile/maestro/voice-draft.yaml
maestro test mobile/maestro/offline-transaction.yaml
maestro test mobile/maestro/database-health.yaml
maestro test mobile/maestro/sync-state.yaml
maestro test -e EXPECTED_QUEUE_ITEM="Maestro очередь" mobile/maestro/sync-queue-retry.yaml
maestro test -e EXPECTED_LOCAL_VALUE="Maestro локальное значение" -e EXPECTED_REMOTE_VALUE="Maestro серверное значение" mobile/maestro/sync-conflict.yaml
maestro test mobile/maestro/document-template-validation.yaml
maestro test -e TEST_DOCUMENT_EVENT_ID=event-id -e TEST_TEMPLATE_NAME="Maestro договор" -e EXPECTED_DOCUMENT_FILE_NAME="Maestro договор №1 от 15.07.2026.docx" mobile/maestro/documents.yaml
```

Для `onboarding.yaml` нужен отдельный подготовленный аккаунт с незавершённым первым запуском. Сценарий завершает мастер на сервере, поэтому перед повторным тестом этот флаг и стартовые данные нужно сбросить в тестовом tenant.

Offline-сценарии сами включают и выключают авиарежим. Если тест был остановлен до последней команды, перед следующим запуском нужно вручную вернуть сеть. Для проверки реальной отправки outbox после восстановления сети требуется доступный API и тестовый tenant; текущие сценарии детерминированно проверяют локальное сохранение и восстановление после убийства процесса.

Фоновая синхронизация проверяется только на development build: после входа экран `Ещё → Синхронизация` должен показать «Включена» либо честное системное ограничение. `database-health.yaml` на том же экране проверяет, что native build действительно открыл SQLCipher и показывает ожидаемую версию схемы. После принудительного завершения во время отправки блок должен отразить число восстановленных операций/файлов; этот data-dependent шаг выполняется вручную, потому что требуется остановить процесс точно в состоянии `syncing/uploading`. В debug-сборке допустимо вызвать worker через Expo Background Task testing API и проверить отправку подготовленного outbox. После logout задача должна исчезнуть из зарегистрированных; повторный headless-вызов без сессии не должен обращаться к CRM API.

`sync-state.yaml` запускается на авторизованном tenant без заранее подготовленных failed/conflict элементов. Flow фиксирует offline-состояние, убивает процесс, проверяет сохранность результата после запуска и затем ожидает чистый успешный цикл после возврата сети. Если tenant содержит проблемную очередь, финальным ожидаемым состоянием будет «Требуется внимание», поэтому перед smoke-прогоном её нужно очистить или разрешить.

Для проверки удалённого отзыва открыть приложение на двух устройствах, отозвать первое со второго и одновременно обновить на первом два экрана. Должен выполниться один refresh-запрос, после серверного `401` первое устройство переходит на вход и снимает background task. Отдельно cloud/API mock возвращает `500`: в этом случае пользователь остаётся авторизованным, а непустой outbox сохраняется и уходит после восстановления сервера.

На экране профиля текущее устройство должно быть явно помечено и не иметь кнопки отключения. Для второго устройства проверяются диалог подтверждения, исчезновение из списка, прекращение bearer-доступа и доставки push. Ошибка сети при загрузке списка показывает retry, а не ложное пустое состояние.

`event-calendar.yaml` использует уже авторизованную сессию, переключает экран мероприятий в month-view и проверяет навигацию по месяцам и возврат к текущей дате. Для проверки счётчиков и перехода в карточку тестовый tenant должен содержать мероприятие или следующий контакт на известную дату; этот data-dependent шаг выполняется в device QA.

`voice-draft.yaml` проверяет bearer AI-контур через ручной текст и не требует микрофона, но требует сети и тарифа с `allowAi`. Системное разрешение микрофона, запись, остановка через две минуты и удаление временного `.m4a` проверяются отдельно на физическом устройстве.

Для `sync-conflict.yaml` в локальной базе должна быть ровно одна нерешённая коллизия. Её подготавливают интеграционным шагом: синхронизируют запись, меняют одно поле в Android без сети, то же поле — на сервере, затем восстанавливают сеть и запускают sync. Значения передаются через `EXPECTED_LOCAL_VALUE` и `EXPECTED_REMOTE_VALUE`; flow принимает серверную версию и проверяет исчезновение конфликта.

Для `sync-queue-retry.yaml` подготавливают одну failed-операцию без конфликта и с доступным сервером для повтора. `EXPECTED_QUEUE_ITEM` — видимое название клиента, мероприятия, транзакции или услуги. Flow проверяет, что пользователь видит запись и может сбросить её backoff отдельной кнопкой; после успешной синхронизации retry исчезает. Для failed-файла используется тот же сценарий вручную с кнопкой `retry-sync-file`, поскольку системная подготовка зашифрованного blob зависит от конкретного устройства.

В расширенной проверке вместе со спорным полем на Android меняют второе, которое web не редактирует. После выбора server/local для конфликта и повторной синхронизации это несвязанное мобильное изменение обязано сохраниться на сервере. Для двух конфликтов решения принимаются последовательно; повторный outbox-patch должен появиться только после решения последнего поля и только в одном экземпляре.

Для `documents.yaml` нужны доступный по тарифу DOCX-шаблон и синхронизированное мероприятие со статусом не `draft`. `TEST_DOCUMENT_EVENT_ID` — ID мероприятия в локальном bootstrap, `TEST_TEMPLATE_NAME` — точное имя шаблона, `EXPECTED_DOCUMENT_FILE_NAME` — ожидаемое имя нового файла с номером и датой. Flow проверяет, что после серверной генерации появляется именно новый файл, а не только уже видимая кнопка шаблона. `document-template-validation.yaml` не открывает системный picker и отдельно проверяет обязательность DOCX-файла; загрузка, замена, скачивание и share sheet остаются device-сценариями с заранее помещённым файлом в Downloads.

Вложения мероприятия проверяются на физическом устройстве отдельно: открыть подтверждённое мероприятие, выбрать изображение или файл до 5 МБ, включить авиарежим до отправки, перезапустить приложение и убедиться, что вложение осталось в очереди. После восстановления сети оно должно перейти в статус синхронизации, появиться в `documentFiles` ровно один раз и открываться через системный share sheet. Повторная отправка того же элемента очереди не должна создавать второй файл.

Не запускайте offline-сценарии параллельно на одном устройстве: они меняют системное состояние сети и используют общую локальную базу.
